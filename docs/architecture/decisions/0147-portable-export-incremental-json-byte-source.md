# ADR-0147：便携归档的增量 JSON 字节源

日期：2026-08-11

状态：已采纳

## 背景

第 152 轮已经提供有界、分块认证的加密信封，但它接收的上游字节尚未定义。当前同步导出会先组装完整 `PrivacyExport`，再调用 `JSON.stringify(payload, null, 2)` 创建完整格式化字符串，最终再创建附件 `Buffer`。即使未来把该 Buffer 交给分块加密，格式化字符串和明文 Buffer 仍会与对象图同时驻留，不能兑现归档链的有界字节处理。

本轮需要先拆掉最终序列化副本，同时保持现有 v4 文件逐字节兼容。该边界必须正确处理 JSON 控制字符、引号、反斜杠、Unicode 代理对与孤立代理项，并能直接作为第 152 轮信封的输入。它不应假装已经解决数据库结果集、照片 base64 或完整 `PrivacyExport` 对象图的驻留。

## 决策

1. 新增内部 `createPortableExportJsonStream()`，输入继续是通过共享契约形成的 `PrivacyExport`，输出是 `AsyncIterable<Buffer>`。不更改公开同步导出的正文、Schema、字段顺序、缩进或末尾换行。
2. 编码语义固定为与现有 `JSON.stringify(payload, null, 2) + "\n"` 逐字节一致：对象沿 JavaScript 可枚举字符串键顺序，数组沿索引顺序，两空格缩进，字符串按 JSON 规则转义，完整代理对保留，孤立代理项写成小写十六进制 `\uXXXX`。
3. 超长字符串和属性名按 UTF-8 预算逐单元扫描；字符不会先组成完整转义字符串。字节聚合器把小 token 写入固定大小 Buffer，默认块为 64 KiB，配置只接受 1 字节至 1 MiB；产出块永不超过配置值。
4. 会话接受可选安全整数 `maximumBytes`。某块会跨越上限时先拒绝、再停止，不输出该块；未来对象上传方必须把该拒绝视为中止未完成对象，而不是可提交前缀。
5. 完成收据只在调用方把生成器推进到物理结束后解析，字段仅含 v4 Schema、配置块大小、精确明文字节数和 SHA-256。源错误、超限或中途取消同时使流与收据拒绝，不能发布部分成功。
6. 组合边界固定为 `JSON bytes → AES-256-GCM envelope → verified plaintext`。测试不得收集超过 8 MiB 的完整 JSON、密文或解密结果，只累计字节数、最大块和摘要；明文收据、加密收据与解密摘要必须对账。
7. 本轮不替换同步控制器。同步路径仍保留既有精确 50 MiB/413 与 `Content-Length` 行为，避免在没有 HTTP 中途错误协议与真实双端回归时改变用户下载语义。
8. 本轮不增加数据库游标、照片流式 base64、KMS、对象存储写入、任务执行器、数据库状态转换、公开 API、下载授权或客户端 UI。

## 影响

- 未来归档执行器可以不创建完整格式化 JSON 字符串和明文附件 Buffer，直接把有界 v4 字节块交给认证加密。
- 逐字节兼容让既有客户端校验器、Schema 版本和数据可携权保持不变；本轮没有迁移公共文件格式。
- 明文 SHA-256/大小与密文 SHA-256/大小形成两个独立完成证据，后续对象上传可以分别对账生成与保管边界。
- 这只移除最终序列化的确定性副本。数据库驱动仍把每个查询结果收集为数组，照片仍整体读取并转为 base64，完整 `PrivacyExport` 仍在编码前存在；R-013 因此保持开放。
- `maximumBytes` 拒绝可能发生在已消费前缀之后。未来上传实现必须支持可靠中止、条件创建和残留清理，不能把前缀对象标为 available。

## 备选方案

### 直接对 `JSON.stringify()` 的字符串做切片

拒绝。虽然输出块看似有界，但完整字符串已经分配，不能减少关键峰值内存。

### 先创建完整附件 Buffer，再交给加密器

拒绝。第 152 轮只能保证自身重分块有界，无法消除调用方已经创建的完整明文 Buffer。

### 立即用数据库 cursor 重写全部 v4 查询

暂缓。训练、餐食、计划和媒体包含嵌套集合与快照一致性要求；在字节格式和完成收据尚未固定前同时改变查询与编码，会放大回归范围。本轮先建立可独立验证的下游消费边界。

### 立即替换公开同步下载

暂缓。当前 HTTP 路径在发送前能返回精确 413 和 `Content-Length`；直接流式响应会引入发送部分正文后才发现超限的错误语义，并需要重新验证 H5 与 WeApp 文件处理。

### 依赖通用 JSON 流式第三方包

拒绝。当前结构固定、算法较小，且关键要求是与既有格式逐字节等价、超长字符串有界及零新增生产依赖；引入通用序列化依赖会扩大供应链和行为面。

## 验证

- 包含中文、emoji、U+2028/U+2029、全部短控制转义、引号、反斜杠、孤立高/低代理项、整数样式键和嵌套集合的 v4 夹具，必须在 7 字节块下与既有序列化器完全相等。
- 每个非空输出块不得超过配置值；字节数和 SHA-256 收据必须与既有产物一致。
- 精确上限少一字节时，流与收据必须拒绝，且已发出的完整块总量不得跨越上限。
- 超过 8 MiB 的超长字符串必须直接经过 JSON 编码、认证加密和认证解密；明文字节数与两个阶段摘要精确对账，JSON/解密块不超过 65,536 字节，加密块不超过 65,557 字节。
- 消费一个块后取消必须拒绝完成收据；非法块大小与最大值必须同步失败。
- 完整格式、类型、单元、集成、构建、生产依赖、中文文档、迁移索引和 Obsidian 门禁通过后才允许提交。
