# ADR-0105：仪表板参考时刻只接纳已发生事实

日期：2026-08-10

状态：已接受

## 背景

Dashboard 接受可选 `at`，并把该时刻作为 `generatedAt`、今日本地日期、7/30/90 日窗口和个人状态账本快照边界。历史日历、健康、营养和动作洞察的 SQL 已经显式拒绝晚于参考时刻的发生事实，计划体验也拒绝 `updated_at > at`；但 Dashboard 的健康、训练和餐食查询只有 91 日下界，没有发生时间上界。纯 `buildDashboard` 同样只按本地日或窗口下界筛选。

因此，一条与参考时刻属于同一本地日、但实际发生在其后的记录，会进入 `today`、`trends`、恢复估计与 `personal-state-ledger-v1`。这会让历史快照知道“未来”，并可能用尚未发生的主观恢复记录影响状态估计。只在客户端隐藏无法修复权威污染；只改 SQL 又会让测试夹具、替代存储或后续适配器绕过边界。

现有 `at` 是发生时间截止，不是事务时点。记录可以在当前创建后按其真实 `occurredAt` 进入较早参考窗口；更正和删除仍使用当前所有者可见版本。修订表保存审计历史，但本轮不把 Dashboard 改造成双时态数据库，也不声称重建过去某时刻看到的旧修订。

## 决策

- Dashboard 的三项来源查询共用同一个 `at` 参数：健康和餐食要求 `occurred_at <= at`，训练要求 `started_at <= at`，并保留原 91 日下界、所有者、确认状态和当前未删除资格。
- `buildDashboard` 在任何 today、readiness、trends 或个人状态计算前，先按同一参考时刻过滤健康、训练和餐食行；晚于参考时刻的计划体验也降为 `null`。这是适配器无关的第二道边界，不依赖调用方先清洗。
- `dashboardSchema` 拒绝 `today.items` 或 `readiness.evidence` 中任何 `occurredAt > generatedAt` 的响应。账本继续逐字段绑定 readiness、七天趋势和计划体验，因此未来恢复证据不能只从其中一个表面漏出。
- 不新增表、迁移、路由、缓存、AI、计划规则或客户端表达。`at` 仍不按 `created_at`、`updated_at` 或修订 `changed_at` 重建交易时间历史；当前更正/删除语义保持不变。
- PostgreSQL 集成测试为同一所有者各写入参考时刻前后的健康、训练和餐食。早期快照必须只含三条，推进参考时刻后必须含六条；这同时证明未来事实被隔离，而不是写入失败或永久删除。

## 影响

Dashboard 的 `today`、7/30/90 日趋势、主观恢复估计和个人状态账本现在共享同一发生时间上界。同一本地日的未来训练、餐食或恢复自评不会提前改变计数、训练量、营养总计、恢复证据数或状态标签。计划体验保持已有更新时间上界。

三项 SQL 多一个可索引的范围谓词，没有迁移和额外查询。当前索引均以所有者和发生时间排序；生产规模性能仍需在共享环境测量。纯投影过滤与 Schema 校验提供失败关闭，但不能证明任意手写趋势计数对应哪些具体原始时间，因为趋势契约只携带聚合值。

本轮明确没有交付双时态历史。较早 `at` 仍读取当前所有者可见修订，已更正或删除的旧内容只能从专用不可变修订账本审计。若未来产品需要回答“当时系统实际知道什么”，应另立带 `changed_at`/修订资格的状态重建决策，不能把本次发生时间截止夸大为该能力。
