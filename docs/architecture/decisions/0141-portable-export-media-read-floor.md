# ADR-0141：便携导出媒体读取前的精确字节下界

日期：2026-08-11

状态：已采纳

## 背景

同步便携导出已有共享 50 MiB 最终 UTF-8 门禁，但原实现会在门禁之前读取全部食物照片和进度照片对象、生成 base64，并构造完整对象图。对于不含媒体也必然超限的账号，这些私有对象读取和字符串分配没有交付价值，还会放大 R-013 的同步内存与 I/O 风险。

数据库照片行包含 `byte_size`，但对象可能已经缺失；当前导出会把缺失对象表示为 `{ unavailable: true }`。因此数据库声明字节数不能单独证明最终导出一定包含对应媒体，用它提前拒绝可能误拒本可合法交付的导出。

## 决策

1. repeatable-read 事务先完成所有者数据、食物照片元数据和进度照片元数据查询，再开始任何 `PhotoStorageService.read()`。
2. 使用同一个 `generatedAt` 和最终集合顺序构造完整 `myfitness-portable-export-v4` 下界；每个照片条目的 `media` 暂设为 `null`，并先经过 `jsonSafe` 与共享 `privacyExportSchema`。
3. 下界沿用最终附件的 `JSON.stringify(payload, null, 2) + "\n"` 与 UTF-8 字节算法。下界超过 52,428,800 字节时，立即返回现有固定 413 `portable_export_too_large`，不读取任何照片对象、不生成 base64，也不分配附件 `Buffer`。
4. `media: null` 是当前三个最终结果的严格下界：没有存储键时保持 `null`；对象缺失时变为更长的 `{ unavailable: true }`；对象存在时变为包含 `contentType`、`encoding` 和 base64 数据的更长对象。等于上限的下界继续执行，不以估算或数据库行数拒绝。
5. 数据库 `byte_size` 继续作为用户导出元数据，但不成为资格拒绝权威。对象存在性和真实字节必须由对象存储读取证明。
6. 控制器对含真实媒体的最终产物继续执行原有精确门禁。服务层下界只增加早期失败路径，不能替代最终附件检查。
7. API 路由、成功 Schema、413 Schema、客户端解释、下载/保存权限和擦除流程均不改变；本轮不实现流式响应、压缩、分片、后台加密归档或真实云存储。

## 影响

- 只要非媒体数据与照片元数据组成的完整 JSON 已经超限，API 就不会再读取食物/进度照片对象，也不会生成对应 base64。
- 合法边界不会因为缺失对象或不可信 `byte_size` 被误拒；最终含媒体大小仍由原门禁精确决定。
- 超限路径仍会加载全部数据库行、构造非媒体对象图并短暂生成一次格式化下界字符串，因此 R-013 只能获得局部缓解，不能关闭。
- 正常导出多执行一次下界格式化与 Schema 验证，换取可证明的媒体读取前资格边界；封闭测试账号规模和内存曲线仍需测量。

## 备选方案

### 汇总数据库 `byte_size` 后提前拒绝

拒绝。对象可能缺失，而缺失对象只导出不可用标记；声明字节数不是最终附件的可靠下界。

### 发现任一大照片就删除媒体或截断集合

拒绝。静默部分导出会破坏用户数据所有权与 v4 完整性，且改变既有成功契约。

### 只保留最终门禁

不采用。它仍保证正确性，但对已由非媒体内容确定超限的账号执行无意义的私有对象读取和 base64 分配。

### 本轮直接改为异步加密归档

暂不采用。该方案需要持久任务、加密密钥、对象保留、下载授权、过期删除和真实托管责任，属于独立交付边界。

## 验证

- 纯测试必须证明下界与最终格式使用相同 UTF-8 计数、精确等于上限时接受，以及 `unavailable`/base64 两种最终媒体表示都大于 `null` 下界。
- 真实 PostgreSQL 与私有对象存储集成测试必须在有实际照片对象的账号上触发下界 413，并证明 `PhotoStorageService.read()` 调用次数为零。
- 既有合法照片导出测试必须继续证明 base64、`Content-Length`、敏感字段排除和成功契约不变。
- 完整格式、类型、单元、集成、构建、生产依赖、中文文档、迁移索引和 Obsidian 门禁通过后才允许提交。
