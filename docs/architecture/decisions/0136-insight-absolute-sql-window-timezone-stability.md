# ADR-0136：洞察绝对 SQL 窗口跨会话时区稳定性

日期：2026-08-11

状态：已采纳

## 背景

动作与健康洞察的公开契约、来源短窗口收据和响应短窗口收据都把 7/30/90 日定义为固定 `days×24h` 的绝对时长。然而数据库窗口查询使用 `make_interval(days => windows.days)`，90 日点查询使用 `INTERVAL '90 days'`。PostgreSQL 对 `timestamptz - 日历日间隔` 会在会话时区中保持本地墙钟时间；跨夏令时边界时，它不一定等于相同天数乘以 24 小时。

独立 `America/New_York` 会话证实该差异。参考时刻位于 2026 年春季跳时之后时，减 7 个日历日的结果比减 168 小时晚 3600 秒；参考时刻位于秋季回拨之后时，结果早 3600 秒。7、30、90 日在所选春秋样本中都跨越相应偏移变化。开发数据库默认 UTC 只是偶然隐藏该缺陷；在其他生产会话设置下，窗口行与点查询/运行时收据会对边界记录给出不同资格。

## 决策

1. 动作和健康三窗口查询的下界统一为 `reference timestamptz - windows.days * INTERVAL '24 hours'`。
2. 两类洞察的 90 日点查询下界统一为 `reference timestamptz - INTERVAL '2160 hours'`。
3. 四个查询继续使用同一个参数化参考时刻、`>=` 包含下界与 `<=` 包含上界；不改变所有者、状态、动作键、指标或已完成组资格。
4. 响应时区只用于本地日期投影和健康 `recordedDays`，不参与绝对窗口成员资格。
5. 单元测试必须同时锁定动作/健康窗口与点 SQL 文本，拒绝重新出现 `make_interval(days => ...)` 或 `INTERVAL '90 days'`。
6. 真实 PostgreSQL 测试必须在显式非 UTC 会话中覆盖春季跳时、秋季回拨以及 7/30/90 日，逐样本证明小时表达式等于 JavaScript 毫秒减法，同时证明日历日表达式确实不同。
7. 不通过把数据库会话全局设为 UTC 来修复。查询自身必须在任何合法会话时区下保持语义稳定，避免连接池、托管默认值或运维漂移重新引入缺陷。
8. 本决策不改变公开 Schema、窗口标签、趋势解释或医疗/训练结论。

## 影响

- 动作/健康窗口行、90 日点集合和双层短窗口收据现在共享同一绝对时长语义。
- 生产数据库会话时区和 DST 不再使边界记录多包含或少包含一小时。
- 恰好 7/30/90 日绝对下界的记录继续包含，早 1 ms 继续排除。
- 响应时区仍能正确生成用户本地日期，但不能把绝对观察窗口隐式变成当地日历日。
- SQL 仅替换四个下界表达式，不增加查询、索引、响应字段或持久状态。

## 备选方案

### 强制所有数据库连接使用 UTC

拒绝作为唯一控制。连接初始化、托管参数或连接池重置可能漂移；查询应自包含其时间语义。UTC 可继续作为运维默认值，但不是正确性的前提。

### 保留当地日历日语义

拒绝。现有契约、点子集收据、Dashboard 趋势和边界测试都明确使用固定 24 小时倍数；改变为当地墙钟日会修改产品含义，并且请求响应时区与数据库会话时区可能不同。

### 在应用中计算四个下界并作为额外参数传入

可行但未采用。显式小时 SQL 已经会话无关，且保持当前参数数量和窗口 CTE；额外参数会扩大调用与测试表面而没有新增证据。

### 依赖现有短窗口收据在冲突时失败

拒绝。失败关闭能阻止错误响应，但不能让合法的非 UTC 部署可用；源头资格应与契约一致。

## 验证

- API 单元测试调用动作与健康服务，锁定两个动态小时下界和两个固定 2160 小时下界，并拒绝旧日历日字面量。
- PostgreSQL 集成测试在 `America/New_York` 会话中交叉 2 个 DST 方向与 3 个窗口长度；六个小时边界全部等于 JavaScript 结果，六个旧日历日边界全部不同。
- 既有动作与健康真实 PostgreSQL 端点测试继续通过，证明资格、聚合、修订与删除行为未回退。
- 定向、完整单元、完整集成、严格类型、格式、生产依赖、中文文档、迁移索引和 Obsidian 镜像门禁通过后才允许提交。
