- 仓库采用 pnpm 工作区，锁文件入库，并共享 CSS/TypeScript 设计令牌包。

- 无第三方运行时依赖的 `myfitness-documentation-migration-index/v1` 扫描 `docs/` 全部 Markdown，要求每份文件恰好归入活跃权威、治理、待迁移专题、待迁移历史或当前受保护序列之一。三个专题批次当前精确登记 17 个路径，六个历史批次要求迭代 000–089 与 ADR-0001–0084 连续且无重复；第 090 轮和 ADR-0085 以后自动扩展连续受保护序列。索引必须保留 Schema、十份受保护活跃文档、191 份待迁移总量、全部批次 ID 和专题链接；它证明范围完整，但不替代翻译准确性、风险时效与技术保真人工审阅。
- 通过父级覆盖限定 pnpm 安全基线：Taro 客户端固定在 Vite 6.4.3/webpack 5.104.1，并使用已修补的解析器与 glob 依赖；未使用的 Less `image-size` 可选解析器被移除，PostCSS/Taro 链的 `nanoid` 固定为 3.3.17。Next 管理端 16.2.11 保留 PostCSS 8.5.19，并移除未使用的旧 Sharp 可选依赖。API 保留 Sharp 0.35.3，Vitest 保持 Vite 8.1.5；生产依赖审计为零个 critical/high，仍登记九个 Taro 构建链 moderate 问题。
- 独立的 `dist-h5` 与 `dist-weapp` 生产目录防止一个平台的构建删除另一个平台产物。无第三方依赖的 `myfitness-client-quality/v1` 校验器测量由入口页推导的 H5 入口、最大异步路由、WeApp vendor/页面包和完整文件树；严格的入库预算在 CI 双端构建后以及不可变发布组装前执行。H5 将至少被两个延迟页面使用的第三方运行时、共享组件和工具抽入异步公共块，再以更高优先级把 Taro 组件运行时拆成独立缓存块；发生时间字段保留最高优先级的专用块。应用启动只加载轻量时区探测器，不再把完整发生时间解析器带入入口。WeApp 由 Taro 内建 `minifyXML.collapseWhitespace` 移除模板格式空白，不改变模板递归层级、组件边界或运行时语义。十一种读取表面共用 `read-authority` 的失败分类，其中九种标准快照读取还共用同一个五阶段纯函数；页面原导出名、类型、文案和权限保持不变，特殊续页阶段不被强行统一。H5 最大异步块与 WeApp 总量预算随实测成果向下收紧。
- 便携导出的 API 与客户端共享 50 MiB（52,428,800 字节）契约。API 先以完整 `media: null` v4 结构建立媒体读取前 UTF-8 下界，再按真实 Buffer、精确 base64 长度和规范 JSON 包装维护每媒体 O(1) 运行下界；初始超限时不读取对象，某个媒体展开后超限时不编码当前对象且停止后续读取。控制器仍对最终格式化 JSON 精确计数，超限时在附件 `Buffer` 分配前返回固定 413 `portable_export_too_large`，合法附件的 `Content-Length` 与正文相等。延迟加载的客户端适配器读取 H5 Blob 或 WeApp 临时文件；无第三方依赖的校验器仍独立要求当前 JSON 媒体类型、精确 v4 信封/集合结构、有效生成时间/账号 UUID 和同一上限，之后才创建 H5 下载锚点或调用 WeApp 持久保存。非成功路径只依 HTTP 413 映射固定 50 MiB 产品说明，不读取或展示响应正文，也不下载、保存、自动重试或推进删除前导出选择；其他非 2xx 保持通用产品文案。成功收据只暴露 Schema 版本、生成时间和字节数；导出内容与账号身份不进入 UI 状态、日志或应用存储，被拒绝的 H5 Blob URL 会被撤销。
- 根命令 `pnpm ops:measure-portable-export` 只接受回环 PostgreSQL，并用随机合成账号和有界数量的无媒体已确认健康记录运行真实便携导出链。严格 `myfitness-portable-export-measurement/v1` 收据只输出夹具规模、接受字节数或固定拒绝码、耗时、进程内存快照、运行时与三项固定限制，不包含账号标识或健康内容；`finally` 删除合成账号及其级联数据。该收据用于复现本地风险，不代表隔离内存分析、生产容量或 SLA。
- 异步归档由共享最小收据/状态机、迁移 0029–0032、内部预约服务、只读 repeatable-read 流事务、三个已协调 keyset 行源与一个独立 workout 头部行源、支持根生命周期和递归懒数组节点的精确增量 v4 JSON 字节源、分块认证加密 codec 和私有对象 multipart writer 组成。预约服务在事务内锁定 active owner，由服务端产生归档 UUID、确定性私有对象键和一小时生成期限；并发同请求只产生一行，同键不同哈希冲突，owner+archive 读取失败关闭，failed/disposed 重放不复活。协调器只校验一次 active owner，在同一快照内依次交付同意事件 `(accepted_at, id)`、健康记录 `(occurred_at, created_at, id)` 与健康修订 `(changed_at, revision, id)`；各段默认 25/最大 100 行，只保存末 UUID 并由数据库回查完整锚点。所有段结束后仍不提交，只有外层 JSON 物理 EOF 调用根 `complete()` 才推进事务 EOF；跳过/重复/乱序字段或任意位置取消均失败关闭、回滚并拒绝统一分集合收据。三种已协调 payload 和 workout 头部 payload 都由 PostgreSQL 先编码并按 UTF-8 计量，最大 64 KiB；超限时不把文本交给 Node，固定错误不含记录标识或内容。真实 PostgreSQL 已证明三集合共享并发隔离、三懒数组 eager/lazy v4 字节相同和字段间取消同根失败；独立 workout 头源另已证明全历史总序、owner 隔离、快照隔离、非部分索引计划与取消同根。信封以 AES-256-GCM 认证 owner/archive/v4/key-ref、final 与物理 EOF。writer 顺序缓冲 5–64 MiB 部件，每部件用 SHA-256 让存储方校验，完整密文摘要/大小只在条件完成成功后发布；源错误、主动取消、上传失败和既有对象冲突都会中止未完成上传，清理失败不掩盖原错。真实 MinIO 已证明 JSON → 信封 → 两部件对象的三层收据一致，三个失败路径无对象或 multipart 残留。公共收据仍排除 key-ref、URL 和令牌。其他十个顶层数组/嵌套聚合/媒体仍完整驻留，workout 头源也未接入协调器或公开 v4，writer 尚未连接归档状态；没有 KMS、租约执行器、公开路由、下载授权或 UI。
- 训练同步导出按 `(started_at, created_at, id)` 固定顶层总序；嵌套 exercises、sets 和 history 分别按数据库唯一的 position、position 和 revision 排序。真实 PostgreSQL 已证明一个被现有 API 契约接受的 30×50 当前训练图在排除 history 后仍超过 64 KiB，而每次修订又保存完整图且修订数没有上限。因此不得把完整 workout 当作现有简单行源的单 payload，也不得提高门禁掩盖结构问题。内部 `createWorkoutSetLayerSnapshot()` 现在以一次 active-owner、只读 repeatable-read 根事务按三元组读取活动与软删除 workout 头、按 position 读取九字段 exercise 头，再按 position 读取十一字段 set；每层都必须恰好一次且完整读取，显式 `complete()` 前不提交。跳过、重复、提前停止和取消会按 set→exercise→root 顺序清理。真实数据库证明 owner/软删除/并发隔离及既有头、动作、组索引可用。本层仍不含 history，不能接入公开 v4 或被称为完成训练流式化；下一步必须分解不可变修订快照。
- JSON 字节源的递归 `PortableExportJsonValue<T>` 类型会保留根 Schema 字段，并把树内每个数组递归映射为 eager 数组或私有 `PortableExportJsonAsyncArray`；业务对象不会因实现普通迭代协议而被自动视为数组。嵌套 workout 单元测试已证明 eager/lazy 字节兼容、字段到达前零拉取，以及活动 sets 取消时内层先关闭、根生命周期后取消。数据库分层会话现已把相同责任落实到 workout→exercise→set 并发布三段收据；history 尚未接入，公开输出仍保持不变。
- 每次导出操作获得单调递增的页面内存代次和纯函数式“已挂载/当前保管责任”提交谓词。卸载、当前概览刷新、撤销恢复进入、账号擦除开始和登出都会使代次失效并清除忙碌状态。延迟适配器在令牌/网络工作前、临时响应读取后、校验后以及 H5 锚点点击或 WeApp 保存前立即检查回调。过期 H5 Blob URL 会被撤销；跨边界完成的 WeApp 持久保存会尽力调用 `removeSavedFile` 回滚。过期操作不发布错误、成功或导出选择，也不会自动重启。
- 同意收据历史是面向追加型 `consent_events` 表的独立只读投影。默认 10 条、最大 20 条的严格分页只暴露收据 UUID、目的、版本、接受时间和可选撤销时间；不返回当前状态字段、用户身份、提供方细节或健康内容。单个 base64url 游标只携带 Schema 版本与收据 UUID。API 在已认证所有者范围内解析该 UUID，并直接用 `(accepted_at, id)` 与数据库锚点比较，不经过 JavaScript 时间戳转换；覆盖所有者/时间/UUID 的索引绑定精确顺序。新增头部事件不会扰动已签发的后续页，客户端仅在 React 内存中保存已接受页面。
- 历史客户端分别建模折叠、初始加载、就绪、刷新、继续加载、初始错误和保留旧数据阶段。首次读取失败不能发布服务器确认的空状态；刷新/续页失败会在页面内存中保留已接受条目和游标，重试只重复同一操作。离线传输、4xx 拒绝、5xx 服务中断和未知适配器失败都有产品自有文案及一个 H5 焦点目标。历史新鲜度从不授予或移除当前同意变更权限，也不增加轮询、持久缓存、后台重放或原始服务消息。
- 每个同意历史请求获得单调递增的代次。折叠只快照其操作和可选游标，随后使代次失效并清除隐藏的忙碌/失败状态；显式重新打开会针对同一意图发起新请求。卸载和父级禁用也会使代次失效。只有代次、打开状态、挂载状态和启用权限仍匹配时，成功、失败、焦点调度和最终忙碌清理才能提交。请求不会被物理中止、持久化或在后台重放。
- 同意历史自有文本使用四个有界组件变量、由内容驱动的按钮行高和显式长令牌换行。在 320 × 844 且精确模拟 2× 变量覆盖时，初始错误、保留的十条前缀、长版本/时间戳标签、底部操作和当前撤销控件都能置于滚动视口内且无水平溢出。由于 Taro 控制 H5 根字号用于视口换算，刻意不使用相对根元素单位。Taro 共享激活守卫证明标准流程中的指针行为，以及大字矩阵中的 Space/Enter 行为；这些只是本地 Chromium 语义，不代表 VoiceOver/TalkBack、浏览器纯文本缩放或微信真机结论。
- 关键 Taro H5 控件使用共享、显式的指针/Enter/Space 激活契约，因为 Taro 自定义按钮元素不会从 `role` 和 `tabIndex` 继承原生键盘激活。适配器还显式输出 `aria-disabled`，并在不可用时阻止指针/键盘回调，因为自定义元素上的裸 `disabled` 属性不具备浏览器原生禁用语义。延迟路由使用稳定元素 ID，并在路由切换后仅对 H5 延迟聚焦；对话框先聚焦安全的取消操作，关闭后返回触发器或稳定回退点。状态表面使用礼貌且原子的播报；减少动态效果的选择器限制在各页面根节点内，不会改变 Taro 路由容器。WeApp 编译保持通过，但 DOM 焦点行为只对已测试 H5 浏览器成立。

## 质量门禁

在下列事项全部可复现之前，MVP 不得进入公开测试：

- 新用户可以完成引导，记录身体、训练、饮食与恢复数据，查看趋势、获取计划，并删除或导出自己的数据。
- AI 推导值绝不在没有用户确认的情况下变成已确认记录。
- 计划输出通过结构、训练负荷、能量摄入和风险措辞校验。
- 权限、账号删除、照片保留、审计日志、备份与事件回滚均完成演练。
- CI 通过格式、代码检查、类型检查、单元测试、集成测试、生产依赖零 critical/high 审计和生产构建。
- H5 与 WeApp 生产文件树通过入库的入口、路由、vendor、页面和总量预算，以及客户端校验运行时回归扫描。
