A dependency-free `myfitness-client-quality/v1` verifier measures the index-derived H5 entrypoint, largest async route, WeApp vendor/page bundles and total trees; strict checked-in budgets run after both builds in CI and before immutable release assembly.
- Critical Taro H5 controls use a shared explicit pointer/Enter/Space activation contract because Taro's custom button element does not inherit native keyboard activation from `role` and `tabIndex`. The adapter also emits explicit `aria-disabled` and blocks pointer/keyboard callbacks when unavailable because the custom element's bare `disabled` attribute is not browser-native disabled semantics. Lazy routes use stable element IDs and delayed H5-only focus after the router transition; dialogs focus the safe cancel action first and return to the trigger or a stable fallback. Status surfaces are polite and atomic, while reduced-motion selectors stay inside each page root so they cannot alter the Taro router container. WeApp compilation remains green, but DOM-focus behavior is claimed only for tested H5 browsers.
- Browser validation accepts an explicit isolated MyFitness API loopback port and forwards the same origin to the API process, H5 build and administrator BFF. The default remains `127.0.0.1:3100`; a collision with another local project no longer requires terminating that process or changing test source, while fixtures cannot be redirected to a remote service.
- Manual nutrition does not initialize the optional photo workflow. `pages/progress-photos/index?kind=food` owns consent, reservation/upload, private candidate recovery, review and deletion on the existing lazy private-photo route. Taro's opener `EventChannel` exists only for that navigation instance and carries only the successful confirmation response's catalog keys/integer grams back to the preserved meal draft; direct visits cannot confirm, and photos, preview paths, consent and unconfirmed candidates never enter URL state or the 24-hour draft vault.
- A dependency-free `myfitness-sensitive-draft/v1` vault protects meaningful unsaved workout, meal and health-record create/correction input for at most 24 hours. Fixed non-identifying keys hold version/kind/owner/time metadata plus one exact page-owned payload; missing scope, cross-owner, invalid, expired or above-96-KiB values are purged. Corrections add only aggregate ID and positive base revision. Restore reads the exact owner-visible current aggregate and proceeds only on an exact revision match, even when the target is outside the first list page; stale/deleted targets are discarded without submitting, while later races still fail through normal optimistic concurrency. Restore is explicit, and save/cancel/logout/erasure initiation clear drafts without touching the separately governed erasure receipt.
- Health-record, workout and meal create recovery treats a transport failure as an unknown result rather than a failed fact. One dependency-free presentation contract separates network ambiguity, retryable HTTP outage, server refusal and unexpected failure. Each editor retains its exact in-memory idempotency key only while the attempted payload remains unchanged; retry reaches the existing server-side user/key/request-hash guard and every payload mutation resets both recovery state and key. Correction requests never receive a create-idempotency promise, and no request is persisted or replayed in the background.
- A separate dependency-free workbench matrix classifies twenty operations across action/food definitions, food/progress photos and weekly-plan generation, decisions, links and AI explanation. Only definition/reservation create can explicitly retry the same in-memory key. Every non-idempotent, evidence-sensitive, destructive or provider-calling stage exposes read-side reconciliation first; server refusal terminates that attempt. Definition correction compares the exact current revision and submitted fields, archive absence proves only loss from active choice, photo-confirm absence never emits unknown draft inputs, and media-delete absence never claims physical byte deletion. Progress-photo upload accepts only the exact ready item and never replays a selected file. Weekly-plan generation reads the exact requested week; decisions require the expected next revision/status and modified selections. Link creation requires the complete plan/session/workout revision tuple; unlink absence proves only that the target is no longer active. AI recovery reads only the original owner/key run, never invokes the worker, and displays completion only after exact plan-revision validation. Food nutrient/reference, progress capture, plan substitution/link and explanation intent remain page-owned input; media paths, photos, requests and replay commands are neither persisted nor queued.
- A dependency-free occurrence resolver maps an explicit `YYYY-MM-DD HH:mm` plus IANA timezone into one offset instant by round-tripping candidate offsets through `Intl.DateTimeFormat`. DST gaps fail, repeated minutes require an explicit UTC-offset choice and future instants fail in both client and shared API contracts. Untouched corrections preserve their exact original seconds/milliseconds; repeats reset time, and workouts expose independently validated start/end fields.
- An authenticated read-only history projection generates exactly 28 requested-timezone local dates ending at its reference instant, then counts current confirmed health records and current non-deleted workouts/meals from the owning user's source rows. It excludes later facts, stores no rollup and recomputes correction/deletion immediately. The client renders explicit blank days without score/adherence semantics; bounded backfill intents accept only a valid date from the previous 90 local days plus a valid IANA timezone and deliberately remain incomplete until the user enters `HH:mm`.
- Current health/workout/meal collection routes return strict `{ items, nextCursor }` pages in occurrence-time, aggregate-creation-time and UUID descending order. ## Quality gates

The MVP cannot enter public beta until all of the following are reproducible:

- A new user can complete onboarding, record body/training/nutrition/recovery data, view trends, receive a plan, and delete/export their data.
- AI-derived values never silently become confirmed records.
- Plan output passes schema, training-load, energy-intake, and risk-phrase validation.
- Permissions, account deletion, photo retention, audit logging, backups, and incident rollback are exercised.
- CI passes formatting, linting, type checks, unit tests, integration tests, zero critical/high production dependency audit, and production builds.
- H5 and WeApp production trees pass checked-in entry/route/vendor/page/total budgets and the client validation-runtime regression scan.
