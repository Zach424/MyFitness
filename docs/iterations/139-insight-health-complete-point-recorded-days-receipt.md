# 第 139 轮：健康未截断窗口与点记录日收据

日期：2026-08-11

状态：已完成

## 1. 范围、分类与验收标准

本轮分类为 F（Consistency Checking）。范围只包含健康 90 日未截断窗口的 `recordedDays` 与完整点集合在响应时区中的去重本地自然日数量之间的收据，以及该路径必要的格式器复用。

验收标准固定为：`recordCount <= 180` 且点数完整时，来源/响应 `recordedDays` 必须精确等于全部点按响应时区投影后的去重本地日数量；`recordCount > 180` 时必须跳过完整记录日对账；同日多点和夏令时重复小时只计一天；真实 PostgreSQL 响应直接证明 90 日窗口等于公开本地日集合。不得从截断前缀复算、使用记录自身时区替代响应时区、自动改值、增加趋势/医疗规则，或修改 SQL、响应形状、客户端、历史记录、计划和 AI。

## 3. 实现方法

### 完整性先于记录日收据

点数收据先证明 `recordCount <= 180` 时来源/响应点集合完整。记录日收据随后运行；零记录继续由空窗口关系验证，超过 180 条立即退出，不把最新前缀冒充完整 90 日集合。

### 响应时区是唯一日期权威

窗口 SQL 使用 `(occurred_at AT TIME ZONE response timezone)::date`。来源收据使用相同响应 IANA 时区格式化 `occurred_at`；响应收据使用已经由 `occurredAt + insight.timezone` 验证的 `localDate`。记录自身 `recordTimezone` 不参与窗口计日。

### 自然日集合而非本地时钟时间

收据只对日期标识去重，不比较小时。纽约 2026-11-01 夏令时回拨时，`05:30Z` 与 `06:30Z` 都显示本地 01:30，但两点的日期都为 2026-11-01，因此 `recordedDays = 1`。

### 格式器按请求复用

初始实现为每个点调用既有 `localDay`，在全量并发测试中使大型 181 点测试超过 5 秒。最终实现让记录日集合使用一个格式器的日期输出，并让健康公开点生成复用另一个格式器；语义不变，全量回归在不提高超时的情况下通过。

### 精确诊断而不修复

来源冲突使用领域级记录日收据错误；共享 Schema 定位 90 日窗口 `recordedDays`。两层都不重写窗口或点，不补造日期，也不解释趋势或健康状态。

## 5. 发现的问题与经验

- 记录数完整不自动证明记录日完整；派生计数也需要独立收据。
- 响应时区决定观察视图的自然日，记录时区只说明原始输入语境，两者不能混用。
- 夏令时重复的是本地小时，不是自然日；按日期集合去重能保持正确语义。
- 共享契约应先验证每个 `localDate`，再使用该字段形成窗口收据。
- `Intl.DateTimeFormat` 配置在一次请求内不变，格式器复用同时改善性能与实现一致性。
- 并发超时可能暴露真实热路径成本；应先消除重复工作，而不是提高测试时限。

## 6. 全局状态、项目反思与下一步

本轮关闭了未截断健康窗口记录日与完整点集合之间的矛盾，同时保持截断边界诚实。当前 90 日收据已经覆盖点数、三项统计和记录日，但 7 日与 30 日窗口仍只受跨窗口单调关系约束。

按 Personal Cognitive Mirror 的 Inspect → Rank → Improve → Validate 反思，第 140 轮应重新排序；当前最小关键候选是健康完整 90 日点集与短窗口子集收据。下一轮需先核对 SQL 的绝对时间闭区间和参考时刻，从完整 90 日点集筛出 7/30 日子集，再核对计数、记录日和统计。必须覆盖边界时刻、空短窗口、同日多点和夏令时；90 日截断时全部跳过。

本轮未新增或关闭风险：记录日收据不证明目标平台 IANA 数据、7/30 日窗口子集、来源真实性、设备准确性、趋势意义、医疗结论或真实用户理解。风险登记册全表时效复核、真实身份/设备/保留/备份与 AI 专家语料仍保持开放。
