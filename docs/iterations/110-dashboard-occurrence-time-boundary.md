# 第 110 轮：仪表板发生时间上界

日期：2026-08-10

状态：已完成

## 1. 范围、分类与验收标准

本轮分类为 E（时间建模）。范围只有 Dashboard 的发生时间截止：健康/餐食的 `occurredAt` 与训练的 `startedAt` 不得晚于请求参考时刻 `at`；相同本地日也不能例外。该边界必须同时覆盖 `today`、7/30/90 日趋势、主观恢复估计和 `personal-state-ledger-v1`。

验收要求固定为三层失败关闭：PostgreSQL 三项查询使用同一个上界；纯 `buildDashboard` 即使收到未清洗行也过滤未来事实和未来计划体验；共享 `dashboardSchema` 拒绝未来 today/readiness 证据。真实集成测试必须先证明早期快照排除三条未来事实，再推进 `at` 证明它们重新出现。不得新增迁移、路由、客户端、AI、诊断、因果或自动计划变化，也不得把发生时间截止夸大为历史修订重建。

## 2. 项目结构、设计、技术与实现功能

- `apps/api/src/insights/insights.service.ts`：健康、训练、餐食 Dashboard SQL 新增 `<= at`；纯投影在所有计算前生成三个合格行集合，未来计划反思也保持为空。
- `packages/contracts/src/insights.ts`：Dashboard 跨权威校验新增未来证据拒绝，确保 `today.items` 和恢复估计证据都不晚于 `generatedAt`。
- `apps/api/src/insights/insights.service.test.ts`：新增纯投影三域/反思未来隔离、Schema 失败关闭和三项 SQL 同参考参数证明。
- `apps/api/src/insights/insights.integration.spec.ts`：新增专属 PostgreSQL 时间边界用例，为同一用户写入参考时刻前后各一条健康、训练和餐食，验证 3→6 条的参考时间推进。
- ADR-0105、架构、路线图、风险登记册、项目状态和本档案：同步 `at` 语义、非双时态限制、验证数据和下一轮防御性点序列方向。

本轮没有客户端视觉变化。用户看到的仍是第 109 轮证据卡和来源入口，但这些表面背后的历史参考快照不再提前吸收未来发生事实。

## 3. 实现方法

### 在查询源头绑定同一个参考时刻

Dashboard 先计算 91 日下界 `since`。三项查询现在都接收 `[userId, since, at]`：健康与餐食使用 `occurred_at >= since AND occurred_at <= at`，训练使用 `started_at >= since AND started_at <= at`。所有者、软删除、确认状态和聚合计算保持原样；没有额外往返或内存拼接查询。

### 让纯投影拒绝未清洗输入

`buildDashboard` 以 `at.getTime()` 建立唯一参考毫秒，在生成 today、readiness、trends 和账本前过滤三个行集合。后续所有计算只引用合格集合，避免某段新代码重新使用原始 `rows`。计划体验已有 SQL 上界，纯函数仍检查 `updated_at <= at`，使测试夹具或替代适配器也不能绕过。

### 用共享契约守住响应边界

`dashboardSchema` 在已有账本一致性校验中读取 `generatedAt`，逐项检查 today 和 readiness 的 `occurredAt`。任一未来时间新增自定义 Issue；计划体验已有 `updatedAt <= generatedAt` 校验，确认恢复账本又必须等于 readiness 最新证据，因此不能只污染其中一个表面。趋势没有原始时间序列，仍由 SQL和纯投影保证。

### 区分发生时间与事务时间

测试和已有产品语义允许“今天补录昨天发生的事实”，所以 `at` 不检查当前行 `created_at`。更正/删除也继续使用当前所有者可见版本，而不是按 `changed_at` 回放旧修订。本轮只回答“该事实当时是否已经发生”，不回答“系统当时是否已经收到、后来是否被纠正”。这种限制写入 ADR 和界面状态文档，防止以后把历史快照误称为完整知识历史。

### 用时间推进排除假阳性

集成用例同一用户创建两组恢复自评、训练和餐食：03:00Z 发生事实位于 04:00Z 参考时刻前，05:00Z 位于其后且仍属同一上海本地日。04:00Z 快照只允许三条、每域计数一；06:00Z 快照必须六条、每域计数二，训练量和能量同时翻倍。这证明后半组真实写入且只受时间资格控制。

## 5. 发现的问题与经验

- 本地日期相同不等于事实已经发生。只按 `localDay === today` 会让当天晚些时候的记录泄漏进中午快照。
- 时间边界不能只在一个聚合层修复。Dashboard 同时驱动 today、趋势、恢复估计和个人状态账本，原始行必须先形成共同合格集合。
- SQL 正确仍不够。纯函数被单元测试、替代适配器和未来数据源直接调用，共享契约又是最终响应门；三层各自阻断不同绕过路径。
- 时间推进是比“结果为空”更强的测试。未来记录随后出现，才能证明过滤不是写入失败、所有者错误或永久删除。
- `at` 的含义必须精确命名。发生时间视图适合趋势和状态窗口，但不能回答系统知识的交易时间历史；混淆两者会产生错误的可解释性。
- 当前趋势契约只有聚合计数，不能从响应自身证明每条来源时间。服务端上界已经修复，后续若引入外部适配器，应继续通过点序列或证据引用提供可审计来源。

## 6. 全局状态、项目反思与下一步

本轮消除了一个会直接污染长期用户认知模型的时间错误：尚未发生的健康、训练或餐食不再提前进入当前/历史状态。它提高了状态准确性、时间一致性和不确定性校准，没有增加任何新功能表面。

全局复查显示，动作和健康洞察的 SQL 已经使用 `<= at`，但其公开纯构造器和共享点序列 Schema 尚未像 Dashboard 一样独立拒绝未来行；当前数据库路径正确，测试夹具、替代适配器或以后抽取的数据源仍可能绕过。下一轮第 111 轮应重新按全局缺口排序；当前最高价值候选是 F（Consistency Checking）：为健康/动作点序列增加纯投影与契约的参考时刻一致性，并以推进时间测试证明，不重复已正确的 SQL。

本轮没有关闭 R-030/R-032：未来事实隔离不会校准恢复阈值，也不能证明状态账本完整或真实用户理解正确。完整双时态历史仍是独立能力缺口；只有出现明确的“当时系统知道什么”产品任务时，才应基于不可变修订 `changed_at` 设计，而不是无界扩张当前 Dashboard。
