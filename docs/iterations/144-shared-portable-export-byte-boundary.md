# 第 144 轮：便携导出共享字节边界与服务端拒绝收据

日期：2026-08-11

状态：已完成

## 1. 范围、分类与验收标准

本轮分类为 R（Risk Reduction）。范围只包含同步便携导出 50 MiB 交付上限的共享契约、服务端最终 UTF-8 资格门禁、稳定 413 收据、成功附件长度证明和客户端既有验证器的常量收敛；不包含流式响应、后台归档、压缩、加密、云对象存储、限时链接、部分导出、真实微信设备或账号规模测量。

验收标准固定为：API 与客户端只能使用同一 52,428,800 字节常量；服务端按与实际附件完全一致的格式化 JSON 加末尾换行进行 UTF-8 计数，精确等于上限时接受，超过一字节时在附件 `Buffer` 分配前返回严格 413 `portable_export_too_large`，且错误体不含账号或导出内容。正常附件必须保持 v4、JSON 媒体类型、文件名、no-store，并使 `Content-Length` 等于实际正文。OpenAPI、架构、PRD、接口与 R-013 必须同步，双端产物不能突破既有预算。

## 2. 项目结构、设计、技术与实现功能

- `packages/contracts/src/privacy.constants.ts` 与 `privacy.ts`：新增唯一 50 MiB 常量、错误码和严格 413 响应 Schema。
- `apps/api/src/privacy/portable-export-artifact.ts`：集中格式化、UTF-8 计数、超限拒绝与附件 `Buffer` 创建；先计数后分配附件。
- `apps/api/src/privacy/privacy.controller.ts`：使用共享序列化器，公开 413 OpenAPI Schema，并为合法附件设置精确 `Content-Length`。
- 服务端、契约与真实 PostgreSQL 测试：覆盖中文内容、末尾换行、精确边界、超一字节、无 payload/data 回显及真实附件字节收据。
- `apps/client/src/lib/privacy-export-verification.ts`：删除本地复制的大小常量，继续从共享契约执行落盘前独立验证。
- OpenAPI 生成物、接口参考、架构、隐私所有权模型、已实现 PRD、路线图、R-009/R-013、项目状态、ADR-0138 与本档案同步实现边界和剩余风险。

本轮没有改变导出 v4 数据集合、数据库查询、快照隔离、照片内容、授权、删除、UI、路由或外部环境。

## 3. 实现方法

### 共享数值与错误契约

把 50 MiB 从客户端私有模块上移到 `packages/contracts`，同时定义固定错误码与四字段 413 Schema。服务端和客户端在编译时依赖同一字面量，后续调整必须同时触发契约、OpenAPI、双端构建和测试变化。

### 先测量字符串，再分配附件

控制器原本直接执行 `Buffer.from(JSON.stringify(...))`。新序列化器先生成完全相同的两空格缩进 JSON 和末尾换行，再用 `Buffer.byteLength(..., 'utf8')` 精确计数。超限路径不会创建附件 `Buffer`；合法路径随后从同一字符串创建附件，因此资格字节与发送字节不存在不同格式。

### 精确包含边界

门禁只拒绝 `byteLength > maximumBytes`。纯测试先取得小型合法夹具的实际字节数，以该数作为临时边界证明精确相等接受，再以下界减一证明超出一字节返回 413。中文字段确保测试不是只覆盖 ASCII 字符长度。

### 固定且最小的拒绝收据

413 只返回状态、错误码、产品自有消息和最大字节数。测试明确拒绝 `payload` 与 `data` 字段；服务端不截断集合、不删除照片、不返回账号标识，也不把超限当作可自动重试的暂时故障。

### 双层保管边界不合并

服务端门禁只证明交付资格。客户端仍读取临时文件并独立验证媒体类型、v4 信封、集合拓扑、时间、UUID 与 UTF-8 大小后才落盘；服务端成功不能替代设备侧证据。

### 如实保留内存限制

超限路径避免附件 `Buffer` 与网络传输，但数据库行、JavaScript 对象图和格式化字符串仍已在内存中。R-013 因此只获得部分缓解，继续要求封闭测试规模测量和后续流式加密限时归档。

## 5. 发现的问题与经验

- 客户端落盘门禁不能代替服务端交付资格；否则无效大文件仍会消耗网络和临时存储。
- 大小限制必须共享为契约，而不是在 API、H5 和小程序各复制一个“相同”数值。
- JavaScript 字符串长度不是 UTF-8 字节长度；含中文和表情的数据尤其不能使用字符数判定附件大小。
- 先 `Buffer.byteLength` 再创建 `Buffer` 可以让超限路径少一份大内存副本，但不能消除已经形成的对象图和字符串。
- 精确包含边界应由测试证明；只测“明显很小”和“明显很大”会遗漏 `>` 与 `>=` 错误。
- 超限导出不能靠静默删除照片或截断历史“修好”，因为数据所有权要求完整性和明确缺失语义。
- 重新构建双端产物是共享客户端契约变化的必要证据；本轮发现两个总量各增加 14 字节，WeApp 余量降至 865 字节。

## 6. 全局状态、项目反思与下一步

本轮让同步便携导出的服务端交付与客户端保管使用同一精确字节契约。合法附件现在有可交叉验证的长度收据，超限产物不会继续分配附件或传输，且不会泄露导出内容。R-013 仍然开放，因为真正的可扩展性问题位于更早的全量查询、对象图和字符串生成阶段。

按 Personal Cognitive Mirror 的 Inspect → Rank → Improve → Validate 反思，第 145 轮应重新排序。当前最小相邻缺口是“便携导出 413 客户端解释与恢复边界”：Taro 下载适配器会把所有非 2xx 响应折叠成通用“数据导出生成失败”，用户无法区分确定性的 50 MiB 资格拒绝与暂时服务故障。下一轮应研究如何在不信任服务端自由文本、不保存错误临时文件、不自动重试的前提下，验证固定 413 收据并展示产品自有的规模/后续归档说明，同时保持删除前“已下载/主动跳过”选择不被错误标记。

本轮未新增、关闭或调整产品风险等级。R-009 因双端各增加 14 字节仍保持开放；R-013 获得服务端交付缓解但不证明 API 峰值内存、封闭测试账号规模、流式加密归档、真实微信文件行为或外部数据保管责任。实际云服务与真实设备配置继续停放。
