# 第 149 轮：便携导出本地规模与内存收据

日期：2026-08-11

状态：已完成

## 1. 范围、分类与验收标准

本轮分类为 R（Risk Reduction）。全局审阅确认 R-013 是当前可在本地继续推进的关键风险，但仓库尚无足以安全实现异步加密归档的保管状态、密钥引用、下载授权和删除责任。因此本轮只建立便携导出真实路径的可复现本地规模/内存收据，不新增公开 API、数据库 Schema、持久任务类型、客户端交互、云服务或真实账号操作。

验收标准固定为：命令只允许回环 PostgreSQL；使用随机合成账号与有界的无媒体已确认健康记录；调用正式迁移、Nest 应用、`PrivacyService.portableExport` 和最终序列化；输出严格且不含账号标识/健康内容的聚合收据；接受和固定 413 均可记录；所有路径最终级联清理；至少完成中等规模、接近 50 MiB 和越界三档实跑；测试与全仓门禁通过。

## 2. 项目结构、设计、技术与实现功能

- `apps/api/src/privacy/portable-export-measurement.ts`：定义记录数边界、回环数据库失败关闭、严格 `myfitness-portable-export-measurement/v1` 收据 Schema 和固定限制。
- `apps/api/src/privacy/portable-export-measurement.test.ts`：覆盖数量边界、协议/主机门禁、IPv4/IPv6 回环和收据最小化。
- `apps/api/src/scripts/measure-portable-export.ts`：迁移本地数据库，创建随机合成账号，以 SQL `generate_series` 写入夹具，运行正式导出/序列化，捕获且只接受精确固定 413，输出聚合 JSON，并在 `finally` 中删除账号和关闭应用。
- `apps/api/package.json` 与根 `package.json`：公开 `pnpm ops:measure-portable-export` 运维入口；记录数由 `PORTABLE_EXPORT_MEASURE_RECORDS` 显式控制，默认 25,000，最大 100,000。
- ADR-0143、架构、隐私所有权模型、路线图、R-013 与项目状态共同记录测量边界、结果、不可外推事项和后续归档责任。

本轮没有改变便携导出 v4 契约、50 MiB 上限、413 产品语义、媒体读取、客户端落盘、账号擦除、生产环境变量、日志或遥测行为。

## 3. 实现方法

### 先对目标数据库失败关闭

配置读取后、迁移和任何夹具写入前解析数据库 URL。只有 PostgreSQL 协议与精确回环主机可以继续，避免一个本地风险工具误写共享环境。记录数也在应用启动前限制为 1–100,000 的整数，防止无界夹具。

### 复用正式导出链而非复制算法

测量脚本使用真实数据库迁移和 Nest 依赖装配，以 `metadata` 模式避免后台任务/外部依赖探测，再调用正式隐私服务与最终序列化函数。一次集合式 SQL 写入只是构造夹具，不绕过导出读取、领域映射、共享 Schema 或字节门禁。

### 聚合收据与敏感数据分离

收据的 strict Schema 只允许夹具数量、结果、耗时、内存与运行时。随机账号 UUID、记录值和导出正文既不打印也不进入收据。固定 caveat 防止把同进程高水位、受 GC 影响的前后快照或无媒体本地夹具误写成生产容量。

### 清理责任独立于结果

合成用户在 `finally` 中删除，其健康记录由所有者外键级联清理；应用关闭位于内层 `finally`，因此删除失败不会被正常关闭伪装为成功。每组运行后再用夹具标记查询验证残留为零。

## 4. 验证证据

- 测量核心纯测试为 1 个文件、3/3 项；API strict 类型通过。
- 最终轻量命令以 10 条记录生成 8,311 字节产物，耗时约 118.62 ms；随后夹具 SQL 计数为 0。
- 默认 25,000 条记录生成 18,904,658 字节产物，耗时约 1,421.59 ms。
- 65,000 条记录生成 49,168,658 字节产物，达到 52,428,800 字节上限的 93.78%，耗时约 4,014.43 ms；RSS 前后快照增加约 349.16 MiB，heap 增加约 315.98 MiB，进程最大 RSS 为 1,115,600 KiB。
- 70,000 条记录由固定 `portable_export_too_large`/52,428,800 字节门禁拒绝，耗时约 3,765.08 ms；RSS 前后快照增加约 223.78 MiB，heap 增加约 233.81 MiB，进程最大 RSS 为 991,516 KiB。
- 四次运行均为 Windows x64、Node v24.14.0、本地 PostgreSQL；夹具不含媒体。`processMaxRssKiB` 包含 ts-node、迁移、Nest 和导出整个进程生命周期，前后快照受 GC 影响，因此这些值只作为风险证据，不是隔离性能基准、预算、生产容量或 SLA。
- 完整单元测试共 92 个文件、483/483 项通过；完整集成共 20 个文件、69/69 项通过；完整 strict 类型、生产构建、格式和差异检查通过。
- 第一次全量单元运行中，一个既有洞察测试在并发负载下超过 5 秒并使该次结果失败；该文件随后独立 12/12 通过，紧接着第二次完整单元 483/483 通过。本轮未修改该测试或放宽超时，最终门禁以成功的完整复跑为准。
- 本轮没有客户端源码、UI、路由或产品文案变化，因此不重复浏览器套件与双端构建；最近完整 Chromium 基线仍为 95/95，H5/WeApp 产物沿用第 146 轮实测。
- 生产依赖审计为 0 个 critical/high、9 个已登记 moderate。
- 中文门禁与迁移索引验证通过：`docs/` 共 321 份 Markdown；十份活跃权威文档、一份治理规范、17 份待迁移专题、174 份待迁移历史，第 090–149 轮和 ADR-0085–0143 连续受保护，待迁移总量仍为 191。
- Obsidian 镜像完成写入并逐字节验证：66,004 字节，SHA-256 为 `236e756e552a7b923798e11c54691dc6974f6a8149ae409e85494f5250bc1b06`；权威来源仍是 `docs/PROJECT_STATUS.md`。

## 5. 发现的问题与经验

- 无媒体的 65,000 条合成记录尚未达到附件上限，进程前后 RSS 已增加约 349 MiB；50 MiB 交付边界不能被误当成 50 MiB 内存边界。
- 最终 413 仍发生在完整数据库结果和非媒体对象图已经构建之后。第 147/148 轮的早拒绝显著减少媒体开销，但没有给同步数据库路径设定峰值内存上界。
- 进程高水位适合证明“本次进程至少到过这里”，不适合用前后差值反推单一阶段。收据必须同时保存运行时与限制，文档只能做保守解释。
- 运维型测量工具也必须具有环境范围门禁、输入上限、敏感输出最小化和可独立验证的清理责任，不能把“仅用于本地”当成安全控制。
- 先形成真实边界证据使后续架构决策更具体：归档状态机必须避免在 API 进程再次完整组装数据库对象图和字符串，否则只把下载时机异步化而没有降低内存风险。
- 当前持久任务与对象存储能力不足以证明加密归档已经成立；密钥引用、保留、下载授权、过期删除与擦除竞态必须先作为数据保管契约设计。

## 6. 全局状态、项目反思与下一步

本轮把 R-013 从“尚未测量账号规模”推进到一份可复现的本地真实路径收据。证据确认 65,000 条无媒体记录的附件已接近固定上限，并伴随显著同进程内存增长；70,000 条能稳定返回既有固定 413。这个结果提高了迁移优先级，但没有关闭风险，也不证明真实用户分布、媒体负担或生产实例容量。

按 Personal Cognitive Mirror 的 Inspect → Rank → Improve → Validate 反思，第 150 轮应先定义异步便携归档的完整保管状态机和契约：所有者请求/幂等、排队、生成、可下载、过期、失败、密钥引用、对象键、短期授权、保留、过期删除、账号擦除竞态和最小收据。只有这些责任清楚且可测试后，才应选择首个数据库迁移与持久任务实现；不能把现有同步 Buffer 或普通对象路径包装成“已归档”。

R-013 保持中等级开放；R-009 和其他风险等级不变。真实云服务、账号、域名、设备与付费 API 继续停放。
