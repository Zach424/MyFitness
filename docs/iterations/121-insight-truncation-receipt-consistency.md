# 第 121 轮：洞察截断收据一致性

日期：2026-08-11

状态：已完成

## 1. 范围、分类与验收标准

本轮分类为 F（Consistency Checking）。范围只有动作/健康洞察的 181 行合格输入上界，以及公开 `hasMore` 与 180 点前缀的最小一致性。

验收标准固定为：两个生产构造器必须在未来过滤后拒绝超过 181 个合格点，182 个原始输入若仅有 181 个当前点仍合法；两个共享 Schema 必须拒绝少于 180 点却声明 `hasMore: true`，同时接受恰好 180 点的真值声明，并保留 `hasMore: false + 180 点` 合法。不得静默截断超限输入，也不得修改 SQL、分页、客户端、响应形状、窗口统计、持久化、计划算法、AI 或健康结论。

- `packages/contracts/src/insights.ts`：新增共享 `validateInsightTruncationReceipt`，两个 Schema 都把不受满前缀支持的真值错误定位到 `hasMore`。

## 3. 实现方法

### 上界只约束合格证据

构造器先保留既有时区、原始顺序和 UUID 唯一性检查，再以参考时刻过滤未来点。181 行上界应用于过滤后的合格集合，因此未来点不会消耗当前截断收据；同一点在参考时刻推进后进入集合时，必须与其余点共同满足上界。

### 真值需要满公开前缀

公开 Schema 已限制 `series` 最多 180 点。新增 refinement 只需在 `hasMore` 为真时要求长度等于 180，就能排除没有公开满前缀的声明。错误归属于布尔收据本身，而不是任一点。

### 假值不冒充完整性证明

恰好 180 个公开点且 `hasMore: false` 可能来自恰好 180 个合格点，也可能来自错误适配器漏掉第 181 点；单个响应无法区分。契约因此不反向要求 180 点必须为真，避免把有限长度虚构成完整性事实。

### 不用静默截断掩盖替代查询

对 182 个以上合格输入继续切片会把“存在一个以上隐藏点”压成与正常 SQL 相同的收据，掩盖适配器或查询上界错误。本轮失败关闭，并保持上游故障可观察。

## 5. 发现的问题与经验

- `hasMore` 是截断收据，不是总数、游标或后续页面承诺；命名相同不能扩大语义。
- 构造上界必须在未来过滤后执行，否则未发生点会错误占用当前证据容量。
- 满 180 点是 `hasMore: true` 的必要条件，但不是充分条件；契约只能验证公开可证明的一侧。
- `hasMore: false` 不能从公开长度证明完整性，尤其在替代适配器边界。
- SQL `LIMIT 181` 仍需纯构造器镜像，因为测试夹具和非 SQL 适配器可以绕过查询保证。
- 上界一致不能证明 181 行查询本身无遗漏、数据库次序完整或隐藏点数量具有产品意义。

## 6. 全局状态、项目反思与下一步

本轮让纵向洞察的截断声明具有可验证的最小公开前缀，并让替代构造输入保持与生产 SQL 相同的有界语义。它没有引入分页，也没有把截断解释为趋势、异常或证据完整性。

按 Personal Cognitive Mirror 的 Inspect → Rank → Improve → Validate 反思，下一处 Foundation Value 较高的缺口位于原始时间值。公开 Schema 已验证时间字符串，但纯构造器直接对原始 `Date` 调用 `getTime()`；`Invalid Date` 会用 `NaN` 绕过排序并在未来过滤中静默消失，改变首点、点数和 `hasMore`。无效参考时刻还会被当前捕获逻辑误报为时区错误。下一轮第 122 轮必须重新排序；当前候选是在排序、过滤和本地日派生前分别验证参考时刻与全部原始点为有限时刻，并覆盖隐藏和未来位置。

本轮未新增或关闭风险：截断收据一致不证明查询完整、未公开点总数、来源真实性、统计意义或用户理解。风险登记册全表时效复核、真实身份/设备/保留/备份与 AI 专家语料仍保持开放。
