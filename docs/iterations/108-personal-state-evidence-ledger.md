# 第 108 轮：个人状态证据账本

日期：2026-08-10

状态：已完成

## 1. 范围、分类与验收标准

本轮分类为 G（自我建模）。它不增加新的记录类型或 AI 功能，而是把已经存在的本人确认、确认记录、系统观察和确定性估计放进一个诚实的当前状态边界，使系统开始回答“知道什么、为何知道、截至何时、什么变化会使它失效”。

范围只有一项可逆的只读投影：复用仪表板原子读取生成非持久化 `personal-state-ledger-v1`，并在现有教练工作台替换六张分散统计卡。验收要求固定并列本人确认体验、确认恢复记录、七天观察窗口和恢复估计/Unknown；每项具备权威、快照、无保证有效期和失效原因；只接受同所有者且精确 `accepted` 的计划反思；来源纠正/删除立即反映；不得新增存储、路由、AI、医疗、因果、依从性或自动计划结论。严格契约、定向测试、完整回归、双端预算、文档、Obsidian 与 Git 都必须通过。

## 2. 项目结构、设计、技术与实现功能

- `packages/contracts/src/personal-state.constants.ts`、`personal-state.ts`：新增策略版本、三种失效原因、四类严格知识条目和完整账本 Schema；`packages/contracts/src/insights.ts` 把账本纳入仪表板并做跨权威一致性校验。
- `apps/api/src/insights/insights.service.ts`：从现有恢复估计、七天趋势和最新合格计划反思即时构造账本；SQL 通过所有者、计划 UUID、修订和 `accepted` 事件约束反思，不持久化派生结果。
- `apps/api/src/insights/insights.controller.ts`：仪表板显式返回 `private, no-store`，避免敏感当前状态被共享或复用为过期结论。
- `apps/api/src/plans/plans.integration.spec.ts`：证明外部所有者不可见，反思纠正后版本/选择更新，删除后账本恢复为空，且响应保持禁止缓存。
- `apps/client/src/pages/index/coach-workbench.tsx`：在原教练首段并列四张证据卡，公开本人确认/当前暂无、确认记录、七天观察、估计/Unknown 和快照无保证有效期；不增加新路由或 CSS。
- `apps/client/src/lib/plan-experience.ts`：计划结果页与教练共用四档本人体验标签，避免两个表面产生不同文案。
- `docs/api/openapi.json`、架构、路线图、风险登记册、ADR-0103、项目状态和本档案：同步契约、设计边界、交付数据、风险与下一轮来源追溯方向。

视觉设计继续采用教练工作台既有的证据脊柱和紧凑卡片网格。首段由“过去七天统计”升级为“个人状态证据账本”，但没有加入仪表盘式评分、颜色诊断、身体评价或 AI 叙事；Unknown 和确认没有记录以不同文字表达。

## 3. 实现方法

### 用一个原子快照引用既有权威

账本与 `today`、`readiness`、`trends` 一起由同一次 Dashboard 构造，因此不需要客户端拼接第二个异步来源。计划体验查询与三类记录查询并发执行；它只连接相同用户、相同计划、相同修订且动作精确为 `accepted` 的不可变计划修订，并拒绝更新时间晚于 Dashboard 参考时刻的反思。未找到反思返回 `null`，不推测“用户没有体验”，历史 `at` 查询也不泄漏未来变化。

### 让 Schema 证明类别和来源，而不只检查形状

每类条目使用固定 `kind`、`knowledgeClass` 和 `authority`。恢复 `state=unknown` 必须对应 `knowledgeClass=unknown`，其他状态只能是 `estimated`。Dashboard 的 `superRefine` 再核对每类快照、七天窗口结束时刻/趋势计数、恢复状态/置信/一致性/标签/证据数，以及确认恢复证据的数量、最近发生时间和来源类型；条目还拒绝借用其他类别的失效原因。测试故意把 Unknown 改写为估计类别或把反思失效原因写入恢复估计，契约都会失败关闭。

### 以失效原因代替虚假有效期

系统不能从当前证据可靠推导一个保证有效截止时刻，因此所有条目都使用 `validUntil: null`。记录与估计声明 `source_record_changed`、`time_advanced`；本人反思声明 `plan_reflection_changed`。客户端公开“无保证有效期”，不显示倒计时或自动刷新，不把页面仍打开当成证据仍有效。

### 保持隐私、纠正和删除沿原权威生效

本轮没有新表或新保留范围。健康/恢复记录继续使用原有更正、软删除和所有者规则，反思继续使用精确修订 PUT/DELETE、便携导出和账号级联擦除。Dashboard 禁止缓存；每次读取都从当前权威重算。集成测试依次创建、纠正、跨所有者读取和删除反思，证明账本没有独立生命周期。

### 在严格包体门禁内保留语义

首个 WeApp 构建因新增表达超过 1,109,000 字节门禁。本轮没有提高预算，而是减少重复属性访问、复用体验标签、压缩重复说明，并保留四类边界、置信、来源含义和无保证有效期。最终只余 84 字节，这已登记为 R-009 的新证据，下一轮不能直接继续叠加客户端代码。

## 5. 发现的问题与经验

- 同一页面展示多项事实不等于拥有一个自我模型。只有明确知识类别、权威、时间和失效边界，系统才不会在 UI 中把本人确认、观察和估计压成同一种“事实”。
- `validUntil` 不能为了界面完整而编造。对滚动健康状态，诚实的答案是没有保证有效期，并公开哪些变化要求重新读取。
- 当前反思必须同时证明所有者和采用修订。仅按用户取最新反思会把历史或未采用计划错误地写入当前状态；SQL 连接不可变 `accepted` 事件把资格放回服务端权威。
- 派生账本不应拥有独立删除接口。让来源更正/删除后即时重算，比同步第二张状态表更能保持隐私生命周期和认知诚实。
- 统一视图也会产生新的过度信任风险。即使类别准确，用户仍可能把四张卡当作完整个人画像；因此 R-032 要求来源追溯和真实用户理解验证。
- WeApp 包体已再次接近硬门禁。功能价值不能成为提高预算的理由；下一轮必须先改变模块边界或减少已有成本，才能安全增加来源控制。

## 6. 全局状态、项目反思与下一步

本轮把系统从“分别展示若干指标”推进到最小的当前自我模型：它知道哪些内容来自本人确认，哪些是确认来源记录，哪些只是七天观察，哪些是确定性估计或 Unknown。它仍没有声称了解完整的人，也没有把这些差异压成故事，因此符合 UNDERSTANDING > FEATURES 与 EVIDENCE > ASSUMPTION。

全局反思显示，下一个缺口不是更多洞察，而是用户控制。账本目前说明了权威类型，却不能从每张卡直接到达既有来源表面进行检查、更正或删除；“可解释”还没有完整变成“可纠正”。因此第 109 轮选择个人状态证据来源追溯：只返回现有记录、计划结果或反思表面，返回后显式刷新同一快照，不把导航成功冒充证据有效，也不新增派生存储或自动推理。实施前必须先解决 WeApp 只余 84 字节的结构约束。

R-030/R-031 仍要求真实纵向校准和非因果理解，R-032 要求验证账本的完整性错觉；风险登记册全表时效复核及所有需要账号、预算、域名、凭据或责任人的托管工作继续停放。
