# 第 152 轮：便携归档分块认证加密信封

日期：2026-08-11

状态：已完成

## 1. 范围、分类与验收标准

本轮分类为 K（Infrastructure）。在审阅当前记录、证据、状态估计、同步导出压力与归档保管链后，最高杠杆本地缺口仍是异步归档的应用层认证加密和有界流格式。范围只增加内部 codec 与单元测试，不接数据库状态、对象存储、KMS、任务执行器、公开 API 或客户端。

验收标准固定为：使用固定版本 AES-256-GCM 分块信封；每帧 nonce 唯一并认证 owner/archive/v4/key-ref 上下文；认证 final 帧阻止完整帧截断；解析器在分配前限制块大小；不规则输入与传输切片可往返；错身份、错密钥、篡改、截断和尾随统一失败；8 MiB 以上输入保持有界输出；只有完整消费才发布精确内部收据；本地密钥生成不被描述为生产 KMS。

## 2. 项目结构、设计、技术与实现功能

- `apps/api/src/privacy/portable-export-archive-envelope.ts`：新增二进制信封头/帧格式、AES-256-GCM 加解密、上下文摘要、认证 EOF、有界重分块/读取器、CSPRNG 数据密钥生成和完成收据。
- `apps/api/src/privacy/portable-export-archive-envelope.test.ts`：覆盖空/非空往返、随机性、上下文/密钥错配、篡改/截断/尾随/超上限、8 MiB 流式往返、配置错误与中途取消。
- ADR-0146 固定字节布局、nonce/AAD 构造、限制、密钥责任和未接入项。
- 架构、隐私所有权、路线图、R-013 与项目状态同步区分“内部 codec 已验证”和“异步导出仍不可用”。

## 3. 实现方法

### 分块认证而不是整包后验认证

每个明文块独立使用 AES-256-GCM。随机 8 字节前缀与 32 位帧序号组成 12 字节 nonce；完整信封头、帧序号和帧头作为 AAD。解码器只有在该帧认证标签通过后才输出明文，所以内存随块大小而不是归档总量增长。

### 把归档身份纳入密码学上下文

固定 JSON 数组按格式、owner UUID、archive UUID、v4 版本和非秘密 key-ref 计算 SHA-256，并写入头部。解码方从所有者限定数据库元数据重建摘要；复制对象、换 owner、换归档行或换 key-ref 都不能通过验证。该摘要不是访问令牌，也不替代数据库 owner 检查。

### 用认证 final 帧定义完整成功

所有数据帧之后还有一个空 final 帧，它使用下一个唯一 nonce 和独立标签。解码器验证 final 后继续检查物理 EOF，因此删除完整尾帧、截断标签或附加垃圾都失败。加密收据也只在 final 输出被完全消费并继续迭代到 done 后解析；调用方中止不能得到“已完成”假象。

### 在读取不可信长度前先固定上限

头部长度固定为 54 字节；解析器先验证 magic、版本、算法、上下文摘要和 1 KiB–1 MiB 块范围，之后才按帧声明长度分配。传输即使一次给出整个对象，有界读取器也只复制当前头/帧所需字节，不拼接完整归档。

### 明确密钥责任边界

codec 接受精确 32 字节数据密钥并只清零自己的副本。CSPRNG helper 证明本地可生成随机候选，但未来执行器必须通过 KMS 数据密钥流程取得明文/包装密钥和非秘密引用，并负责调用方副本清零；本轮没有持久化任何密钥材料。

## 4. 验证证据

- 新增 1 个单元文件、6/6 项定向测试通过；空/非空与逐字节传输分片均可往返，内部收据的格式、算法、块数、明文/密文字节数和 SHA-256 精确一致。
- 同一密钥/上下文/明文的两次加密产生不同密文；两个 CSPRNG 数据密钥不同。
- 错 owner、错 archive、错 key-ref、错密钥、密文篡改、截断、尾随字节和 1 MiB 以上声明块均被固定 `portable_export_archive_envelope_invalid` 拒绝。
- 8,388,745 字节确定性输入在不收集完整密文/明文的情况下边加密边解密，摘要一致；加密输出块最大不超过 65,557 字节，解密块最大不超过 65,536 字节。
- 31 字节密钥与 1,023 字节块配置同步失败；消费首个输出块后取消使完成收据拒绝。
- 完整单元测试为 94 个文件、493/493 项；完整集成为 21 个文件、72/72 项，均已通过提交前全量门禁。
- 本轮没有客户端源码、UI、路由或产品文案变化，因此不重复浏览器套件与双端构建；最近完整 Chromium 基线仍为 95/95，H5/WeApp 产物沿用第 146 轮实测。
- 生产依赖保持 0 个 critical/high、9 个已登记 moderate；完整 strict 类型、生产构建、格式、中文和文档索引门禁均通过。
- Obsidian 镜像完成写入并逐字节验证：66,861 字节，SHA-256 为 `0f84c84ded3c2248ab68b83a4087d588508e2ac139630717c741637e57a6649d`；权威来源始终是 `docs/PROJECT_STATUS.md`。

## 5. 发现的问题与经验

- 认证加密的“可流式写出”不代表“可流式安全读出”。单一 GCM 标签只有结尾可验证；分块 AEAD 才能在有界内存下做到验证后输出。
- 逐帧标签仍不能证明序列完整，必须额外认证 EOF；否则在完整帧边界截断会留下全部有效的前缀。
- nonce 随机并不足以表达同密钥内唯一性。每信封随机前缀加帧计数器让局部唯一可证明，而每归档新数据密钥仍由未来 KMS 策略负责。
- Promise 收据不能在生成器配置失败前被创建为永久 pending。把密钥长度等配置校验前移后，已创建会话才能保证完成或拒绝。
- 测量“单个产出块有界”比一次 RSS 快照更直接证明 codec 的内部输出约束，但仍不代表未来查询、JSON 编码、SDK 上传或整个 worker 的峰值内存。

## 6. 全局状态、项目反思与下一步

本轮为异步归档增加了可版本化、可认证、可流式消费的应用层格式，并让错误身份、篡改和不完整对象在进入未来下载链前失败关闭。它保护的是长期健康/训练/饮食证据的保管完整性，不改变任何用户状态估计，也不会把更多数据误当成认知事实。

按 Personal Cognitive Mirror 的 Inspect → Rank → Improve → Validate 反思，下一轮应重新比较三个缺口：可增量产生 v4 JSON 的所有者快照游标、支持背压/校验和/条件写入的私有对象上传、以及 KMS 数据密钥 lease。优先选择能以真实测量减少完整数据库行/JSON 驻留且不要求真实云账号的最小边界，而不是直接增加公开预约或伪执行器。

R-013 保持中等级开放；R-009 和其他风险等级不变。真实 KMS、云存储、账号、域名、设备与付费 API 继续停放。
