# 第 159 轮：便携归档健康历史同事务根生命周期

日期：2026-08-11

状态：完成

## 1. 范围、分类与验收标准

本轮分类为 K（Infrastructure）。第 158 轮已经指出两个独立快照不能代表同一事实时刻，而且字段间没有活动懒数组可保管事务；因此本轮优先修复快照正确性和连接生命周期，不增加第三个数据集合。

验收标准固定为：健康记录与修订必须共享一个 repeatable-read 事务和一次 active owner 校验；严格按 v4 字段顺序延迟读取；第二字段结束后也不能先于完整 JSON EOF 提交；完整消费解析统一分集合收据；活动字段、字段间空隙或后续 JSON 取消均回滚。真实数据库还必须证明第一字段后的并发新增不进入第二字段、双懒数组与 eager v4 逐字节相同，以及字段间取消时第二源未启动且双收据共享根错误。

范围不迁移 `consentEvents` 或其他集合，不实现生产聚合服务、KMS、租约执行器、公开路由、下载授权、客户端入口或同步导出切换。

## 2. 项目结构、设计、技术与实现功能

- `apps/api/src/privacy/portable-export-database-snapshot.ts`：新增同事务健康历史协调器、私有字段边界、严格顺序/单次消费、延迟根提交、统一分集合收据和显式取消。
- `apps/api/src/privacy/portable-export-json-stream.ts`：新增可选 `PortableExportJsonStreamLifecycle`；完整物理 EOF 触发根完成，失败或取消触发根清理并保留有序错误。
- 两个单元测试文件新增四个场景，证明一次流/一次 owner 校验、根提交时机、字段间同根取消、JSON 根回调时机与清理双错误保真。
- PostgreSQL 组合测试新增两个场景，证明同快照跨字段隔离、双懒 v4 字节兼容，以及 1 字节块字段间取消回滚。
- ADR-0153 固定字段边界与根生命周期；架构、数据库、隐私、已实现 PRD、路线图、R-013 和项目状态同步更新。

## 3. 实现方法

1. 读取第 158 轮状态、档案和 ADR-0152，重放现有 JSON token/异步数组关闭链及数据库 EOF 提交语义。
2. 先识别两个不同空隙：第一字段与第二字段之间没有活动迭代器；第二字段结束与整个 JSON EOF 之间数据库也不能提前提交。
3. 把两个行源的 active owner 校验与页面读取拆开，独立方法保留原入口；新协调器只校验一次 owner，再在同一事务中发送行与显式边界。
4. 第二边界后暂停底层迭代器，由会话 `complete()` 才请求物理 EOF；`cancel(error)` 对任意暂停阶段调用底层 `return()`。
5. JSON 字节源在最后一块已交付、调用方继续请求 EOF 时执行根 `complete()`；任何捕获错误或外层 `return()` 则构造/保留一个根错误并执行 `cancel()`。
6. 单元测试先用可观测假数据库证明提交与回滚时序，再用真实 PostgreSQL 在字段之间插入一组记录/修订，排除两个事务伪装成一个快照的可能。
7. 以 `chunkBytes: 1` 在健康字段刚结束时取得确定性调度点，确认修订生成器尚未启动，再取消外层 JSON 并比较两个收据的错误对象。
8. 运行目标测试后执行完整单元、集成、strict 类型、生产构建和全部治理门禁。

## 4. 验证证据

- 目标 JSON/数据库快照单元测试为 2 个文件、17/17 项通过；目标 PostgreSQL 快照组合为 1 个文件、9/9 项通过。
- 完整单元为 98 个文件、515/515 项；完整集成为 23 个文件、85/85 项。
- 可观测假数据库只建立一个流并执行一次 owner 查询；两集合均读完时仍未提交，调用根 `complete()` 后才提交并解析 `{ healthRecords, healthRecordRevisions }` 收据。
- 真实 PostgreSQL 在健康记录字段结束后插入第三条记录及修订；既有修订字段仍只返回原两条，新会话能返回三条。
- 两个懒数组的 43 字节块输出与 eager v4 完全相同，JSON 字节数/SHA-256 与两集合批次/行数收据均对账。
- 1 字节块在字段间停止时修订源尚未启动；外层 `return()` 触发回滚，JSON 与统一数据库收据保留同一 `portable export JSON stream did not complete` 错误对象。
- 完整 strict 类型和生产构建通过；H5 仍只有已登记的 308 KiB 入口预算与 Taro webpack cache 警告，本轮没有客户端源代码变化。
- 完整格式、生产依赖、中文与文档索引门禁均通过；生产依赖为 0 个 critical/high、9 个已登记 moderate。
- Obsidian 镜像完成写入并逐字节验证：68,503 字节，SHA-256 为 `7ba872b11a86696d18aaa2bcaeecc7518acb8838c6bdcd0ed08bff7fe9763a07`；权威来源始终是 `docs/PROJECT_STATUS.md`。

## 5. 发现的问题与经验

- “两个查询共享一个生成器”仍不足以定义文件级事务；必须明确谁在最后字段之后拥有提交权。
- 内层 `for await` 只覆盖活动数组取消。字段间空隙和根尾部都需要外层生命周期，资源所有权不能靠隐式迭代器传播猜测。
- 数据库物理 EOF 是提交条件，但文件级成功需要把推进 EOF 的权力交给 JSON 根；边界事件使数组可以结束而事务不结束。
- 字段边界不能预取下一字段的首行，否则取消测试即使回滚，也已经违反按需读取和最小暴露原则。
- 统一收据应保留各集合统计而不暴露游标或内容；这既便于容量分析，也避免把数据库实现细节提升为公共契约。
- 1 字节块不是生产配置，而是有用的并发调度证明工具：它把字段结束与下一字段开始之间的短暂状态变成可复现验收点。

## 6. 全局状态、项目反思与下一步

本轮让健康当前事实与修订历史首次成为同一事实时刻的可携带片段，并把文件成功、数据库提交和取消回滚绑定到同一个根生命周期。这提升了 Personal Cognitive Mirror 对纵向事实的可验证性，没有改变健康事实、AI 判断或用户界面。

Inspect → Rank → Improve → Validate 的下一步可迁移体量较小、已有 `(accepted_at, id)` 稳定历史顺序的 `consentEvents`。实现前必须先确认其同步投影、payload 边界和在 v4 中早于健康记录的字段位置，再把现有两集合协调器泛化为顺序集合描述，而不是复制第三套状态机。三集合仍须共享一次 owner 校验、一个事务和一份根收据。

R-013 保持中等级开放；R-005、R-009 和其他风险等级不变。真实 KMS、云存储、账号、域名、设备与付费 API 继续停放。
