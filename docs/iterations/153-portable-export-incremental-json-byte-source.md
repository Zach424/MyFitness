# 第 153 轮：便携归档增量 v4 JSON 字节源

日期：2026-08-11

状态：已完成

## 1. 范围、分类与验收标准

本轮分类为 K（Infrastructure）。审阅同步导出的四层驻留后，按“影响 × 置信度 × 基础价值 / 成本”比较了数据库游标、对象流式上传、KMS lease 与增量 JSON：对象上传尚需明确校验和、长度、条件创建和中止语义；本地 KMS 抽象不会减少内存；数据库游标会同时触及全部嵌套集合。最高置信的最小改进是先移除最终完整格式化字符串和明文附件 Buffer。

范围只增加内部 v4 JSON 字节源和组合测试，不替换同步下载，不接数据库游标、照片流式 base64、对象存储、KMS、任务执行器、状态转换、公开 API 或客户端。

验收标准固定为：与现有漂亮打印 v4 JSON 逐字节一致；超长字符串、转义、Unicode 与孤立代理项分块正确；每个输出块有界；大小/SHA-256 收据只在完整消费后发布；超限与取消失败关闭；超过 8 MiB 的字节源可直接流经上一轮认证加密并逐块验证解密，三个阶段字节/摘要对账；文档必须明确剩余完整对象图风险。

## 2. 项目结构、设计、技术与实现功能

- `apps/api/src/privacy/portable-export-json-stream.ts`：新增递增 JSON token 编码、UTF-8 有界聚合、大小门禁、SHA-256 与完成收据。
- `apps/api/src/privacy/portable-export-json-stream.test.ts`：新增五项测试，覆盖格式等价、精确超限、超过 8 MiB 的加密组合、取消/配置拒绝与独立消费。
- ADR-0147 固定兼容格式、字符串/Unicode 处理、块边界、收据生命周期与未接入范围。
- 架构、隐私所有权模型、已实现 PRD、路线图、R-013 与项目状态同步区分“最终 JSON 副本已可消除”和“数据库对象图仍完整驻留”。

## 3. 实现方法

### 逐 token 产生既有漂亮打印格式

编码器按现有字段与集合顺序遍历 `PrivacyExport`，对象和数组只写入结构 token、换行与两空格缩进。它不调用整包 `JSON.stringify()`；数字和布尔值使用运行时规范标量表示，字符串由专用扫描器逐单元转义。最终单独写入一个换行，保持同步产物字节不变。

### 在超长字符串内部保持有界

扫描器识别引号、反斜杠、五种短控制转义、其余控制字符、完整 UTF-16 代理对和孤立代理项。普通 Unicode 保留，孤立代理项写成规范小写 `\uXXXX`。待写 token 达到字节预算即交给固定 Buffer 聚合器；因此一个数 MiB 的 base64 或文本值不会先形成同样大小的转义副本。

### 让完成证据跟随物理消费

编码会在逐块产出时累计精确字节数与 SHA-256。只有调用方继续迭代到生成器结束才解析收据；消费首块后取消、源错误或超过配置上限都会拒绝。超限判断发生在产出当前块之前，因此已产出的完整块总量不会跨过门禁。

### 直接组合而不收集完整产物

大值测试把 JSON `AsyncIterable<Buffer>` 直接交给 AES-256-GCM 信封，再把密文生成器直接交给认证解码器。测试只累计最大块、总字节和摘要，不拼接完整 JSON、密文或明文；明文收据、加密收据与解密摘要必须一致。

## 4. 验证证据

- 新增 1 个单元文件、5/5 项定向测试通过；连同既有导出产物与加密信封测试为 3 个文件、16/16 项。
- 7 字节块下，中文、emoji、U+2028/U+2029、控制字符、引号、反斜杠、孤立高/低代理项、整数样式键与嵌套集合均与既有 `serializePortableExport()` 逐字节一致。
- 上限比最终产物少一字节时，字节流与完成收据同时拒绝，已发出块不跨越上限；消费一个块后取消同样拒绝收据。
- 超过 8 MiB 的单一长值完成 JSON → 加密 → 认证解密管线；解密字节数、JSON SHA-256、加密明文收据与解密摘要相等，JSON/解密块不超过 65,536 字节，加密块不超过 65,557 字节。
- 完整单元测试为 95 个文件、498/498 项；完整集成为 21 个文件、72/72 项，均已通过。
- 本轮没有客户端源码、UI、路由或产品文案变化，因此不重复浏览器套件与双端构建；最近完整 Chromium 基线仍为 95/95，H5/WeApp 产物沿用第 146 轮实测。
- 完整 strict 类型、生产构建、格式、生产依赖、中文和文档索引门禁均通过。
- Obsidian 镜像完成写入并逐字节验证：67,104 字节，SHA-256 为 `8bfcd41ba7edaf9f7965c818ab8bfec0e50a5980bb3c5322590dafd3fc9d2951`；权威来源始终是 `docs/PROJECT_STATUS.md`。

## 5. 发现的问题与经验

- 把完整字符串切成小 Buffer 只是“小块输出”，不是增量序列化；必须从字符串转义内部开始分块，才会消除最终字符串副本。
- JavaScript 字符串按 UTF-16 代码单元索引。若随意切开代理对，UTF-8 编码会产生替换字符并破坏逐字节兼容；完整代理对、孤立高代理项和孤立低代理项必须分别处理。
- 流式上限可能在已经交付前缀后才触发，所以下游对象写入必须具备中止和残留清理语义；仅有 `maximumBytes` 不能保证对象存储原子性。
- 收据在最后一个块被读取时仍不能发布，调用方必须继续请求并观察 `done`；这阻止“拿到全部看似有效块但未验证源正常结束”被当成完成。
- 本轮组合测试证明 JSON 与 codec 的内部块有界，不证明数据库驱动、照片读取、AWS SDK 上传或整个 worker 的 RSS 有界。

## 6. 全局状态、项目反思与下一步

本轮让未来归档链第一次从 v4 语义对象直接进入认证密文字节，而无需创建完整格式化 JSON 和明文附件 Buffer。格式、来源字段和用户数据可携权保持不变；它改善的是隐私证据的可保管性，没有增加用户记录、推断或 AI 权威。

按 Personal Cognitive Mirror 的 Inspect → Rank → Improve → Validate 反思，下一轮应重新比较：在 repeatable-read 下按有界批次产生各 v4 集合、为现有私有对象服务增加背压/校验和/条件创建/中止能力，以及 KMS 数据密钥 lease。优先选择能继续减少完整数据库行和对象图驻留、且能以真实 PostgreSQL 或本地对象存储证明的边界。

R-013 保持中等级开放；R-009 和其他风险等级不变。真实 KMS、云存储、账号、域名、设备与付费 API 继续停放。
