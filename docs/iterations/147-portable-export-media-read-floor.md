# 第 147 轮：便携导出媒体读取前的精确字节下界

日期：2026-08-11

状态：已完成

## 1. 范围、分类与验收标准

本轮分类为 R（Risk Reduction）。范围只包含同步便携导出的数据/照片加载顺序、精确下界、复用的 UTF-8 字节门禁、纯测试、真实 PostgreSQL/私有对象存储集成测试和相应文档；不包含客户端、公开 Schema、照片内容、截断/降级、流式响应、后台归档、压缩、加密、云服务或真实设备。

验收标准固定为：所有数据库集合和两类照片元数据读取完成后、任何照片对象读取前，必须构造可证明不大于最终附件的完整 v4 JSON；下界超过 50 MiB 时必须返回既有固定 413，且 `PhotoStorageService.read()` 为零次。下界等于上限时不得拒绝；数据库 `byte_size` 不得充当对象存在性或最终附件字节权威。合法导出、对象缺失语义与控制器最终精确门禁必须保持不变。

## 2. 项目结构、设计、技术与实现功能

- `apps/api/src/privacy/privacy.service.ts`：把进度照片元数据查询移动到首个媒体读取之前，复用同一 `generatedAt` 构造 `media: null` 的完整导出下界，验证通过后才按原顺序读取两类私有对象。
- `apps/api/src/privacy/portable-export-artifact.ts`：抽出唯一格式化函数、`portableExportByteLength` 与 `assertPortableExportWithinLimit`；下界和最终附件共享相同的缩进、末尾换行、UTF-8 计数和 413 收据。
- `apps/api/src/privacy/portable-export-artifact.test.ts`：锁定测量/附件字节一致、精确边界接受，并证明 `null` 小于对象缺失和 base64 两种最终媒体表示。
- `apps/api/src/privacy/privacy.integration.spec.ts`：真实创建账号与已净化照片，在服务下界被压低的测试门禁拒绝时证明 413、无正文数据和对象存储读取零次；既有正常导出仍验证真实 base64。
- ADR-0141、架构、路线图、R-013 与项目状态同步记录实现边界和剩余风险。

本轮没有修改数据库 Schema、公开 API、OpenAPI、客户端、UI、路由、产品文案、照片保留/删除权限或 AI 行为。

## 3. 实现方法

### 从最终大小反推单调下界

最终照片条目只有三种媒体结果：没有存储键时为 `null`，对象缺失时为 `{ unavailable: true }`，对象存在时为带 base64 的对象。使用相同父对象、集合顺序和 `generatedAt`，把所有媒体暂设为 `null` 后得到的格式化 UTF-8 字节数不会大于任何最终结果，因此“下界已经超限”足以安全拒绝。

### 不把声明元数据提升为事实

`byte_size` 描述入库时的已净化 JPEG，但导出时对象可能已缺失。若按声明总和拒绝，一个对象全部缺失的账号可能本可导出不可用标记却被错误拒绝。本轮只依赖当前可序列化对象图的精确字节，不依赖行数、字符数或媒体估算。

### 下界与最终门禁共用算法

格式化函数保持 `JSON.stringify(payload, null, 2)` 加一个换行。纯测量和最终 Buffer 都经过同一个字节断言，避免早期和最终门禁的空白、编码或边界漂移。服务层只增加下界检查；控制器仍对读取真实媒体后的最终对象再次精确检查。

### 用真实对象证明没有读取

集成测试先通过正式上传路径创建实际私有照片，再监听真实 `PhotoStorageService.read()`。测试只把同一精确断言的上限压到 1 字节，使真实元数据下界确定触发 413；断言发生于对象读取之前，因此调用次数保持为零。正常集成用例仍读取同类对象并验证 base64，防止测试替身掩盖成功路径。

## 5. 发现的问题与经验

- 精确持久化字段不一定是当前对象事实；只要对象生命周期允许缺失，数据库 `byte_size` 就不能单独证明最终导出大小。
- 安全早拒绝需要证明单调关系，而不只是“通常会更大”。`null` 到当前两种对象表示的格式化字节关系可以由纯测试复现。
- 早期门禁和最终门禁职责不同：前者只拒绝已由下界确定不合格的请求，后者仍决定真实附件能否交付。
- 在真实存储路径创建对象、再证明读取调用为零，比只对纯函数做 mock 更能说明 I/O 顺序已经改变；压低测试上限只是触发同一生产算法，不改变服务编排。
- 并行运行 CPU/数据库密集套件会制造与改动无关的 5 秒超时；应保留第一次失败并用定向加串行全量复核，而不是扩大超时掩盖资源争用。
- 这轮减少了确定超限路径的媒体 I/O/base64，但正常请求多一次下界字符串，数据库结果和非媒体对象图仍在内存中；不能把局部优化描述成流式或有界内存。

## 6. 全局状态、项目反思与下一步

本轮首次在媒体对象读取前建立了不误拒的同步导出资格边界。对于不含任何照片内容也已经超过 50 MiB 的账号，API 现在直接返回既有 413，不再读取私有对象或生成 base64；正常导出和最终字节权威保持不变。

按 Personal Cognitive Mirror 的 Inspect → Rank → Improve → Validate 反思，第 148 轮仍应优先处理 R-013，但范围应限制为“媒体展开后的精确增量下界”。应审计 base64 长度和格式化包装的可计算增量，在读取每个对象后、生成当前 base64 和读取后续对象前再次精确拒绝，并用多对象夹具证明不会产生 O(n²) 全量重序列化。若无法证明增量与最终格式逐字节等价，应保持现状，不用近似公式成为拒绝权威。

R-013 获得局部缓解但保持中等级开放：完整数据库行、非媒体对象图和下界 JSON 仍同步生成，正常导出还会生成最终字符串；异步加密归档、规模测量与限时交付尚未完成。R-009 和其他风险等级不变，真实云服务、账号、域名、设备与付费 API 继续停放。
