# 第 112 轮：营养参考本地日期序列一致性

日期：2026-08-10

状态：已完成

## 1. 范围、分类与验收标准

本轮分类为 F（Consistency Checking）。范围只有营养长期洞察的 90 日本地日期与 7/30/90 日窗口来源。输入必须恰好覆盖 `generatedAt` 在请求 `timezone` 中的本地日以及此前 89 个自然日；顺序、日期和窗口必须全部一致。

验收标准固定为失败关闭：纯 `buildNutritionInsight` 在窗口派生前拒绝错序、重复、未来、缺日和整体偏移，不自动排序、去重或补零；共享 `nutritionInsightSchema` 独立定位首个日期错位，并逐字段重算三个固定窗口。同一输入在较早参考日失败、推进到末日后通过。不得修改已正确 SQL、路由、客户端、持久化、营养目标、饮食处方、AI 或自动计划。

- `packages/contracts/src/insights.ts`：新增参考本地日、自然日移动、窗口重算和逐字段匹配；顶层营养 Schema 同时验证日期与窗口来源。
- `apps/api/src/insights/insights.service.test.ts`：现有营养投影用例新增较早参考时刻与反序输入失败证明。

- ADR-0107、架构、路线图、风险登记册、项目状态和本档案：同步失败关闭语义、验证证据、R-029 限制和下一轮历史日历候选。

本轮没有视觉变化。正常 PostgreSQL 仍返回相同 90 日与窗口；新增边界只在内部来源或响应不一致时阻止发布。

## 3. 实现方法

### 从参考时刻计算唯一日期范围

服务端先用既有 IANA 时区格式化把 `at` 映射为末日本地日期，再把该 `YYYY-MM-DD` 作为 UTC 日历日期执行自然日增减，生成从末日前 89 日到末日的有序数组。该算术不把本地日假设成固定毫秒长度，因此跨 DST 仍按自然日连续。

### 在窗口派生前失败关闭

构造器要求输入长度为 90，且每个 `local_date` 与同索引预期日期相等。任一不匹配都抛出 `nutrition insight rows must cover the reference local-date range`。不排序是为了暴露 SQL/适配器顺序错误；不补行是为了避免把未知来源状态变成“已确认无摄入”。只有完整合格序列才进入既有单日映射和窗口计算。

### 让最终响应独立重建窗口来源

契约层重新计算末日本地日并生成 90 日预期数组，只为首个错位点添加精确 Issue，避免整体偏移时产生 90 条重复错误。随后按固定索引分别取最后 7、30、90 日，重算 recorded/missing、meal/item/fiberKnown 计数和五项可空营养总计。任一窗口顺序或字段不一致都在对应 `windows[index]` 失败。

### 修正被新边界揭示的夹具

旧契约夹具从 `2026-07-01` 到 `2026-09-29`，数组长度虽然为 90，却实际跨越 91 个含端点自然日；旧 Schema 只检查长度，所以没有发现整体缺了一日。起点修正为 `2026-07-02` 后，正常响应、日期门禁和窗口重算同时成立。

## 5. 发现的问题与经验

- 数组长度正确不代表日期跨度正确；必须用参考日生成每个预期日期，而不是只比较首尾或检查升序。
- 对缺失证据自动补空白日会隐藏上游故障。只有权威 SQL 正常生成的空白日才能表达“该日本地范围内没有已确认餐食记录”。
- 自然日不能用固定 86,400,000 毫秒在本地时区递推。先获得本地日期，再用 UTC 日历算术移动日期，可避开 DST 日长变化。
- 窗口内部自洽仍不代表来源正确。只有从已接受 90 日序列重算并逐字段比较，才能防止窗口与公开日序列分叉。
- 错误报告应失败关闭但保持有界。整体偏移只报告首个错位位置，足以定位问题且不会制造巨量 Issue。
- 强化契约会暴露历史夹具中的语义欠账；修复夹具比放宽边界更能保护长期时间模型。

## 6. 全局状态、项目反思与下一步

本轮把营养观察从“长度为 90 的数组”提升为可证明的 90 日本地时间轴，并把三个汇总窗口绑定到该时间轴。它提高了纵向饮食记录的时间完整性和来源一致性，同时继续把缺失记录保持为未知而非零摄入。

全局复查显示，跨领域历史日历的 SQL 已正确生成截至 `at` 的 28 个本地日，但 `buildHistoryCalendar` 会从任意输入复制 start/end，共享 Schema 只要求两端等于数组并严格升序；一个间断、未来或整体偏移的 28 日数组仍可通过并驱动错误回填日期。下一轮第 113 轮应重新按全局缺口排序；当前最高价值候选是继续归类 F（Consistency Checking），为历史日历补精确参考范围与连续性，不重复已正确 SQL，也不改变零行为/依从性语义。

本轮没有关闭 R-029：服务器端 IANA 映射和确定性自然日门禁不能证明真实 H5/微信平台时区数据。R-030/R-032 与双时态历史同样保持开放。
