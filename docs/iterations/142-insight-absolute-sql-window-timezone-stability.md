# 第 142 轮：洞察绝对 SQL 窗口跨会话时区稳定性

日期：2026-08-11

状态：已完成

## 1. 范围、分类与验收标准

本轮分类为 F（Consistency Checking）。范围只包含动作/健康洞察四个 SQL 下界与既有绝对 `days×24h` 产品契约之间的跨数据库会话时区一致性，以及证明该规则所需的 SQL 文本和真实 PostgreSQL DST 测试。

验收标准固定为：先在非 UTC PostgreSQL 会话中复现日历日间隔相对固定小时区间的跨 DST 差异；再把动作/健康三窗口下界统一为 `windows.days * INTERVAL '24 hours'`，把两类 90 日点下界统一为 `INTERVAL '2160 hours'`。四个查询必须保留 `>=` 下界、`<= at` 上界和其他资格不变；春季跳时、秋季回拨与 7/30/90 日六个组合都必须等于 JavaScript 毫秒边界。不得只依赖 UTC 运维默认值、放宽收据、改变响应形状、当地日期投影、客户端、历史记录、计划或 AI。

## 2. 项目结构、设计、技术与实现功能

- `apps/api/src/insights/insights.service.ts`：替换动作窗口、动作点、健康窗口、健康点四个日历日下界为显式小时区间；查询参数、资格、排序和限制不变。

本轮没有改变合法响应形状、客户端行为或持久化结构。

## 3. 实现方法

### 先复现，不把 UTC 当证明

开发数据库初始 `TimeZone = UTC`，日历日与固定 24 小时在该会话中恰好相等。独立会话先执行 `SET TIME ZONE 'America/New_York'`：春季参考时刻减 7 个日历日比 168 小时晚 3600 秒，秋季参考时刻则早 3600 秒。这证明问题来自 PostgreSQL `timestamptz` 与日间隔语义，不是 TypeScript 浮点或格式化差异。

### SQL 自包含绝对语义

窗口 CTE 已提供整数 `windows.days`，因此直接乘以 `INTERVAL '24 hours'`。固定 90 日点查询使用 2160 小时，避免仍以日单位表达同一边界。小时分量按绝对时长作用于 `timestamptz`，不随会话时区的 UTC 偏移变化；不需要新增参数或连接初始化钩子。

### 四个下界一起迁移

只修窗口或只修点都会触发完整点/短窗口收据冲突。动作与健康各有窗口和点两条查询，本轮一次替换全部四处，并用单元测试同时检查；仓库内生产洞察代码不再保留 `make_interval(days` 或 `INTERVAL '90 days'`。

### 双向 DST 与三个窗口长度

真实测试交叉两个参考时刻和 7/30/90 三个长度。每行把 PostgreSQL 小时边界转换为 UTC ISO 字符串，与 `referenceAt.getTime() - days×86_400_000` 精确比较；同时要求旧日历日结果不同，避免测试样本没有真正穿过偏移变化。春季和秋季方向相反，防止只覆盖单向一小时差异。

### 保持日期投影独立

绝对资格边界不使用用户请求时区。健康 `recordedDays` 与逐点 `localDate` 仍按响应 IANA 时区投影；动作/健康原始 `recordTimezone` 或数据库会话时区都不改变窗口成员身份。

## 5. 发现的问题与经验

- `timestamptz - INTERVAL '7 days'` 不等价于固定 168 小时；会话时区是运算语义的一部分，而不只是输出格式。
- 开发环境为 UTC 可能隐藏跨 DST 缺陷；测试应主动切换到有偏移变化的代表性会话。
- 失败关闭收据能阻止矛盾数据发布，但不能替代让生产查询本身满足契约。
- 查询自包含的小时语义比依赖连接初始化更稳健，尤其适合连接池和托管数据库。
- 修复共享时间资格必须同时覆盖窗口与点、动作与健康；只改一条路径会制造新的快照矛盾。
- DST 测试应覆盖春秋两个方向，并断言旧表达式确实不同，避免选择了没有穿越偏移的无效样本。
- 用户响应时区、记录来源时区和数据库会话时区是三个不同概念；只有第一个参与本地日期展示，三者都不应改变绝对窗口时长。

## 6. 全局状态、项目反思与下一步

本轮关闭了动作/健康洞察在非 UTC PostgreSQL 会话中可能多取或少取一小时边界记录的缺陷，使 SQL 资格、完整点集和运行时收据真正采用同一绝对窗口。R-029 的服务端缓解证据得到加强，但客户端平台 IANA 数据与真机行为仍保持开放。

按 Personal Cognitive Mirror 的 Inspect → Rank → Improve → Validate 反思，第 143 轮应重新排序；当前最小关键候选是产品风险登记册全表时效与责任门禁复核。风险表最近一次完整审阅停留在第 043 轮，此后大量实现和发布证据已经变化，且 R-022 等缓解描述出现过期。下一轮应逐项核对所有开放风险的当前事实、等级、仓库证据、外部责任前提和关闭条件；不得用本地测试替代真实账号、设备、责任人、政策或托管批准。

本轮未新增或关闭产品风险：显式小时 SQL 不证明目标平台 IANA 数据、真实记录时间、设备准确性、用户理解、趋势或医疗/训练意义。外部身份/设备/保留/备份、AI 专家语料与托管材料仍保持开放。
