# 第 145 轮：便携导出超限拒绝的客户端解释边界

日期：2026-08-11

状态：已完成

## 1. 范围、分类与验收标准

本轮分类为 R（Risk Reduction）。范围只包含同步便携导出收到 HTTP 413 时的客户端产品解释、错误正文信任边界、临时文件释放、下载/保存/重试副作用禁止和删除前导出选择保持；不包含服务端超限算法、错误体 Schema 解析、异步归档、流式加密、部分导出、真实微信文件系统、云对象存储或账号规模测量。

验收标准固定为：客户端只能依 HTTP 413 状态识别确定性的同步规模拒绝，文案中的 50 MiB 必须来自共享 `maximumPrivacyExportBytes`；不得读取、解析、显示、记录或持久化服务端自由文本。413 必须释放 H5 临时 Blob，不触发 H5 下载、WeApp `saveFile`、自动重试或 `exportChoice` 推进。真实 H5 流程必须以恶意 `message` 证明产品文案可见、恶意文本不可见、下载数为零且删除步骤仍为“尚未选择”，随后旧 v3、错误媒体类型与合法 v4 流程仍可按原边界工作。

## 2. 项目结构、设计、技术与实现功能

- `apps/client/src/lib/privacy-export-verification.ts`：新增只接收状态码的 `privacyExportHttpFailureMessage`，413 映射为固定产品说明，其他状态不进入该分支。
- `apps/client/src/lib/privacy-export-download.ts`：非 2xx 在读取正文前结束；413 使用固定说明，其他状态保留通用失败文案，并先释放 H5 临时 Blob。
- `apps/client/src/lib/privacy-export-verification.test.ts`：锁定 413 的精确 50 MiB 文案，并证明 500 不会误入规模拒绝解释。
- `tests/e2e/privacy.spec.ts`：在既有导出验证流程前注入含恶意自由文本的 413，证明信任边界、零下载与删除选择不推进；随后继续验证旧版本、错误媒体类型和合法 v4 下载。
- 架构、隐私所有权模型、已实现 PRD、接口参考、路线图、R-009/R-013、项目状态与 ADR-0139 同步记录本轮边界。

本轮没有修改 API 响应、导出 v4 内容、授权、账号删除、路由、页面布局、视觉样式或真实外部环境。

## 3. 实现方法

### 状态码是唯一错误输入

下载适配器已经拥有跨 H5/WeApp 一致的 `statusCode`，因此把 413 映射放在无 I/O 的纯函数中。函数不接收响应对象、正文、错误码或后端消息，从类型表面缩小可被误用的输入；其他非 2xx 继续返回既有通用产品文案。

### 文案复用共享数值

说明中的 MiB 数值由 `maximumPrivacyExportBytes / (1024 * 1024)` 计算，不复制第二个 50 或 52,428,800 字面量。单元测试锁定当前中文结果，使共享契约变化必须显式更新产品说明和验证证据。

### 先释放临时资源，再终止副作用

适配器在所有非 2xx 分支先调用已有 H5 临时文件释放函数，然后抛出 `ApiError`。控制流在读取文件、验证 JSON、创建下载锚点或调用 WeApp `saveFile` 之前结束；现有自动重试仍只属于一次 401 会话刷新，413 不进入该路径。

### 删除选择不由失败推导

页面只有收到已经本地验证并实际完成下载/保存的成功收据后才把 `exportChoice` 标为 `downloaded`。413 只展示失败反馈，浏览器测试直接检查删除步骤仍显示“尚未选择”，避免把错误解释误当作数据保管完成。

### 对恶意正文做负向证明

浏览器夹具返回合法状态码但带有大写恶意 `message`。断言只查找产品说明并明确要求恶意文本数量为零，因此即使未来适配器试图把后端自由文本带入 UI，测试也会失败。Chromium 对刻意的 413 请求会产生一条预期控制台网络错误；测试精确计数这一条，同时继续拒绝其他浏览器错误。

### 隔离本地端口冲突

定向浏览器验证发现 `127.0.0.1:3100` 已由用户另一个 `D:\Study\blog` 本地服务占用。本轮没有停止或修改该服务，而是使用 `MYFITNESS_TEST_API_PORT=3110`，临时按相同 API 基址构建测试 H5；验证完成后重新生成默认 3100 基址的正常 H5 产物，并重建 WeApp。这个处理保持了其他项目状态与仓库测试源码不变。

## 5. 发现的问题与经验

- 能解释确定性失败不等于必须解析错误正文；状态码足以提供保守产品说明时，更窄的输入面更容易跨 H5/WeApp 保持一致。
- 后端自由文本不应自动获得 UI 权威。代理错误页、实现细节或恶意内容都可能绕过产品审核。
- 失败路径的资源释放、下载禁止和状态不推进需要同一条端到端证据；只测试提示文字不足以证明保管边界。
- 413 是确定性资格拒绝，自动重试不会改变数据规模，还可能制造重复负载与误导反馈。
- 浏览器会把刻意的 4xx 记录为控制台网络错误；测试应精确允许预期条目，而不是关闭全部错误审计。
- 本地测试端口可能被无关项目占用。隔离端口并恢复正常构建比终止用户的其他服务更安全，也让验证来源明确。
- 必要产品说明仍有包体成本；WeApp 余量由 865 字节降至 548 字节，下一轮必须优先恢复可持续增长空间。

## 6. 全局状态、项目反思与下一步

本轮补齐了服务端 413 收据之后的用户解释边界：用户现在能知道当前版本无法同步生成超过 50 MiB 的副本，同时产品不会读取错误正文、伪造下载成功或自动重复请求。R-013 仍然开放，因为峰值内存、账号规模、异步归档和真实微信文件行为没有变化。

按 Personal Cognitive Mirror 的 Inspect → Rank → Improve → Validate 反思，第 146 轮应重新排序。当前最高优先级本地缺口是 R-009：WeApp 距既有总量预算只余 548 字节。下一轮应先对生产产物做归因，再选择一项语义等价且可逆的代码、模板或静态资源收敛，至少恢复 1 KiB 余量；不得提高预算，也不得删除本轮安全说明、隐私约束、错误状态或无障碍语义来换取数字。

本轮未新增、关闭或调整风险等级。R-009 因余量进一步收窄而更紧迫；R-013 获得客户端解释缓解但仍受同步内存和归档缺口限制。真实云服务、账号、域名、设备与付费 API 继续停放。
