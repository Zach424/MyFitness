# 第 132 轮：健康 90 日窗口与点截断收据

日期：2026-08-11

状态：已完成

## 1. 范围、分类与验收标准

本轮分类为 F（Consistency Checking）。范围只有健康 90 日完整窗口记录数、最多 181 行来源点、180 点公开前缀和 `hasMore` 的收据关系。

验收标准固定为：先证明真实窗口与点 SQL 使用同一 90 日资格边界；`recordCount <= 180` 时来源行数必须精确相等，`recordCount > 180` 时来源必须恰有 181 行；公开响应必须满足 `series.length = min(recordCount,180)` 与 `hasMore = (recordCount > 180)`；缺失 90 日来源行只有在零合格点时可继续回退为空；真实 PostgreSQL 响应必须证明窗口计数等于未截断点数。不得从有限前缀臆测更多明细，不得重算统计、补零或修改 SQL、响应形状、分页、客户端、历史值、计划、AI 与医疗解释。

## 3. 实现方法

### 先确认同一资格集合

窗口与点 SQL 都限定同一所有者、请求指标、confirmed、未删除、参考时刻上界和 90 日下界。只有在资格集合一致时，完整计数与有限点查询才可形成收据；本轮不尝试把 7/30 日窗口与 90 日点混合比较。

### 来源层精确收据

来源点先完成时间、数值、UUID、指标、来源、单位、换算、顺序、唯一性和未来过滤。随后最多 181 行门禁先阻止过取，再根据完整 `recordCount` 计算期望行数：不超过 180 取全部，超过 180 必须取到第 181 条收据。缺失 90 日窗口视为零，因此只有零点可通过。

### 响应层可观察关系

公开 Schema 已能看到完整 `recordCount`、最多 180 点和 `hasMore`，因此无需猜测：点数必须等于计数与 180 的较小者，更多标志必须精确等于计数是否超过 180。错误分别落在窗口计数和标志路径，便于替代适配器定位。

### 不从有限前缀重算统计

超过 180 条时，公开点只是最近前缀，不能重算完整窗口的 minimum、maximum 或 average。即使不截断，窗口统计仍由数据库聚合权威提供；本轮只核对基数收据，不改变统计来源。

## 5. 发现的问题与经验

- 局部门禁全部正确不代表组合响应一致；完整计数、有限收据、公开前缀和布尔标志必须形成关系约束。
- 181 行不是任意上限，而是 180 点公开边界的一条可验证更多收据。
- 稀疏回退不能无条件生成空窗口；一旦同资格点存在，缺失窗口就是证据矛盾。
- `hasMore:false + 180 点` 是否合法取决于可见的完整计数；有完整计数后不再需要“无法区分”假设。
- 新断言插入相似测试块时必须核对 describe 上下文；测试名称相同不代表契约类型相同。
- 平均值不具有跨窗口单调性，不能由基数收据顺带推导。

## 6. 全局状态、项目反思与下一步

本轮关闭了 90 日窗口宣称、点查询收据、公开前缀和更多标志彼此矛盾的路径。它没有验证三个嵌套窗口之间的集合关系。

按 Personal Cognitive Mirror 的 Inspect → Rank → Improve → Validate 反思，下一处同类缺口位于 7/30/90 日窗口的跨行单调性。较长窗口包含较短窗口，因此记录数和记录日不能减少，非空较长窗口的 minimum 不能更高、maximum 不能更低；average 没有单调性。下一轮第 133 轮必须重新排序，当前最小候选是在保留稀疏来源回退的前提下，让来源和公开响应分别验证这些集合不变量，不补造缺失统计或解释数值好坏。

本轮未新增或关闭风险：点收据一致不证明跨窗口单调、记录真实性、设备准确、健康范围、趋势意义或真实用户理解。风险登记册全表时效复核、真实身份/设备/保留/备份与 AI 专家语料仍保持开放。
