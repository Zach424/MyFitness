# 第 091 轮：中文项目记录治理

日期：2026-08-05

状态：已完成

## 1. 范围与验收标准

本轮只处理项目记录语言治理，不修改客户端、API、数据库、AI 服务或部署运行时。验收要求是：四份活跃权威文档具有稳定的中文一级、二级导航；项目状态的目标、模块总览、状态词汇和质量门禁完成中文化；建立明确的中文写作、术语和历史迁移规则；第 090 轮起的迭代档案与 ADR-0085 起的架构决策由同一个本地/CI 命令检查中文标题、日期/状态字段、最低正文规模和中文占比；技术字面量、链接与历史英文证据不得被误改；全量单元、类型、格式和生产依赖门禁保持通过；状态与本档案同步到 Obsidian 后逐字节核对，并以一次 Conventional Commit 提交。

历史 0–89 轮档案和 ADR-0001–0084 不在本轮批量翻译，因为它们是既有审计证据，大范围改写难以确认语义未漂移。四份活跃文档的详细英文正文也按后续受控轮次处理；本轮先建立可执行契约，避免迁移过程中继续产生新的英文记录。

## 2. 项目结构、技术与设计状态

- `scripts/docs-language-policy.mjs`：无第三方运行时依赖的中文文档检查器，导出测量与仓库验证函数，同时提供失败关闭的命令行入口。
- `scripts/docs-language-policy.test.ts`：覆盖技术字面量/链接排除、中文记录通过、英文记录拒绝和活跃标题回退拒绝。
- `docs/DOCUMENTATION_LANGUAGE_POLICY.md`：中文权威来源、自动检查边界、术语表、写作和迁移规则。
- `docs/architecture/decisions/0086-chinese-documentation-governance.md`：记录编号门槛、活跃导航契约、历史豁免和人工审阅边界。
- `docs/PROJECT_STATUS.md`、`docs/product/ROADMAP.md`、`docs/architecture/ARCHITECTURE.md`、`docs/operations/USER_IDENTITY_RUNBOOK.md`：一级、二级导航改为中文；项目状态的活跃总览进一步中文化。
- `package.json` 与 `.github/workflows/ci.yml`：增加 `pnpm docs:check-language`，CI 在格式检查之后运行。
- `AGENTS.md` 与 `README.md`：把新记录中文要求加入每轮协议，并公开本地检查入口。

门禁 Schema 为 `myfitness-chinese-documentation/v1`。它不进入产品包，也不读取用户数据、Obsidian 内容或网络资源。

## 3. 实现方法

### 用编号门槛区分新增约束与历史证据

检查器扫描 `docs/iterations` 中编号不小于 090 的 Markdown，以及 `docs/architecture/decisions` 中编号不小于 0085 的 Markdown。这样可以对用户提出要求后的记录立即失败关闭，同时让既有英文档案保持可审计，等待单独翻译。门槛写入代码和 ADR，后续只能前进，不能用降低门槛或改名来绕过规则。

### 把技术字面量排除在语言比例之外

自然语言测量先移除围栏代码块、行内代码、Markdown 链接和 URL，再统计汉字与拉丁字母。每份受检记录至少需要 200 个汉字，且汉字占两类字符总量的 60% 以上。这样保留 `OIDC`、命令、路径、Schema 和环境变量，不鼓励为通过指标而翻译代码。一级标题仍必须包含中文，元数据必须使用 `日期：YYYY-MM-DD` 和 `状态：`。

### 把活跃导航作为稳定契约

项目状态、路线图、架构基线和用户身份运行手册分别登记必须存在的中文导航标题。检查器精确读取仓库文件并比较标题集合；恢复英文标题、误删或改写关键入口都会失败。详细正文迁移仍由人工逐段审阅，不由比例工具自动翻译。

### 保持一个权威来源

语言门禁只读取仓库，不编辑 Obsidian。格式和内容定稿后，仍使用既有同步器把 `docs/PROJECT_STATUS.md` 精确复制到 vault；本轮档案另做同名精确副本与 SHA-256 核验。语言治理没有引入第二份可编辑项目状态。

## 4. 验证证据

- 中文文档定点测试通过 1 个文件、4/4 项；先发现并修正了测试夹具同时返回两类记录而断言只预期一条的问题。
- `pnpm docs:check-language` 验证 4 份活跃权威文档、迭代档案 090–091 和 ADR-0085–0086；每份新增记录均超过 200 个汉字和 60% 中文占比。
- 完整 Vitest 通过 82 个文件、423/423 项；严格 TypeScript 工作区检查通过；Prettier 全仓格式检查通过。
- 生产依赖审计仍为 0 个 critical/high，9 个已登记 moderate。
- 本轮不修改产品运行时代码、构建配置或依赖锁，不重跑 API/PostgreSQL 集成、AI 评估、客户端构建及 97 项浏览器场景；沿用第 089–090 轮相应证据，且不把本轮表述为新的运行时证明。
- `docs/PROJECT_STATUS.md` 与 Obsidian 权威状态镜像逐字节一致；本档案在 vault 的 `iterations` 目录中保存同名副本并通过 SHA-256 核验。

## 5. 发现的问题与经验

- 只把新档案改成中文并不足以形成长期约束；没有 CI 门禁时，下一轮仍可能因复制旧模板而恢复英文元数据。
- 直接统计所有 ASCII 字符会惩罚路径、命令和协议名，诱导无意义翻译。先移除技术边界，再计算自然语言比例更符合维护目标。
- 语言比例只能发现明显回退，不能判断翻译是否准确，也不能证明风险、验证和下一步是否完整，因此必须保留人工审阅与一轮一档案协议。
- 一次性翻译全部历史文档会把数十轮语义变更压进一个提交，难以审计。编号门槛既保护历史证据，也明确从哪一轮开始执行新规则。
- 活跃导航标题比全文比例更适合作为稳定接口：它让责任人立即获得中文入口，同时给详细正文留下可控迁移空间。

## 6. 全局状态、剩余风险与下一步

从本轮开始，新增迭代与架构决策的中文记录要求可以在本地和 CI 复现，不再依赖口头约定。项目状态入口、模块总览和四份活跃文档导航已中文化，但当前架构长条目、风险表、路线图历史行、架构规则与身份运行手册仍包含大量英文，不能声称整个文档库已经完成中文化。

第 092 轮继续处理活跃权威正文：优先翻译项目状态的当前架构和风险、路线图的发布门禁、架构基线的仓库/数据规则，以及身份运行手册；同时提高门禁对这些活跃段落的覆盖。翻译必须保持链接、代码字面量、风险级别、验证数字和历史语义不变。

真实云账号/预算、域名/TLS、微信/OIDC 提供方、生产对象存储/KMS、数据责任人、集中遥测、政策备案、真实 WeApp 文件系统和获批付费模型金丝雀仍需用户或外部系统输入，继续停放且不视为已完成。
